# 직군별 출발 표

설치할 때 읽는 키트 파일이고 설치하지 않습니다. 여기서 직군 표를 골라 `SUBAGENT_GUIDE.md`의 모델 배정 표로 쓰고, 그 직군의 「지시문 체크리스트 기본 줄」을 `SUBAGENT_BRIEF_CHECKLIST.md`에 더합니다. 설치한 뒤 하는 일이 크게 바뀌어 직군을 더할 때는 이 파일을 Claude에게 보여 주고 지금 표에 합쳐 달라고 합니다. 이미 있는 일 이름의 칸과 표시(「(고정)」, 시험 표시, 최저선)는 그대로 두고 새 이름만 더합니다. 회고로 실측한 칸이 출발 표의 추정보다 정확하기 때문입니다. `config.json`의 `removedKinds`에 든 이름은 더하지 않고 사용자에게 다시 넣을지 묻습니다(다시 넣으라고 하면 표에 넣은 뒤 `--restore-kind "<일 이름>"`). 다만 표에 `<이름>[기준]` 꼴 칸이 있는 이름은 회고가 쪼갠 옛 이름이라 묻지도 더하지도 않습니다. `config.json`의 `roles`에도 그 직군(이 문서의 직군 절 제목 그대로)을 더합니다. 표에 새 일 이름을 더하면 그 칸 정의의 `~/.claude/agents/<정의>.md` description 일 이름 나열에도 같은 이름을 더하고(나열이 없는 정의의 꼴은 `RETRO.md`의 4단계), `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --check`의 「정의 description과 표 칸이 다른 곳」이 `없음`인지 봅니다.

이 표들은 출발점입니다. 표에 없는 일은 쓰면서 기록되고, 회고 때 표에 더해집니다(`RETRO.md`의 4단계).

## 표 형식

직군마다 둔 모델 배정 표는 모두 아래 형식을 지킵니다(지시문 체크리스트 기본 줄의 표는 아래 「지시문 체크리스트 기본 줄」의 형식입니다). 회고 스크립트(`subagent-retro.js`)가 이 형식으로 표를 읽어 일 이름을 뽑기 때문입니다.

- 머리줄은 `| | low | medium | high | xhigh |`이고, 모델 줄은 `| **Haiku** |`, `| **Sonnet** |`, `| **Opus** |`로 시작합니다.
- 한 칸의 일 이름은 쉼표로 나눕니다. 괄호 안은 부연이라 일 이름에 들어가지 않고, 괄호 안의 쉼표로는 나뉘지 않습니다. 괄호는 이름 끝에만 둡니다. 이름 가운데 있으면 스크립트가 그 괄호를 이름에서 빼서, 이름을 기록에 그대로 적은 줄이 표 밖 일로 잡힙니다. 「」는 이름의 일부로 남습니다(「무조건 Opus」). 스크립트가 이름에서 떼는 표시는 시험 표시, 고정 표시, 최저선 표시뿐입니다. 표에는 `「(고정)」`, ``「(최저: `<정의>`)」``, ``「(시험: 다음 1건 `<정의>`)」``처럼 낫표까지 적고, 낫표 없는 `(고정)`, ``(최저: `<정의>`)``, ``(시험: 다음 1건 `<정의>`)``도 같은 표시로 읽고, 최저선 표시는 정의 이름의 백틱 없이도 읽습니다.
- 이름 뒤의 `「(고정)」`은 내려 보지 않는 칸의 표시이고, ``「(최저: `<정의>`)」``는 그 정의 아래로 내려 보내지 않는 칸의 표시입니다. 직군 표를 합칠 때 두 표시를 지킵니다. 표의 Haiku high 칸과 Opus low 칸은 내려 보기 시험 자리라 비워 둡니다.
- 빈 칸은 비워 둡니다. 칸 수는 모든 줄이 머리줄과 같아야 합니다.

## 모든 표에 남는 칸

체계가 스스로 쓰는 칸이라 어느 직군을 골라도 지우지 않습니다.

| 칸 | 일 이름 | 쓰는 곳 |
|:---|:---|:---|
| Haiku medium | 회고 정정 분류 「(고정)」 | `RETRO.md`의 2단계가 표에서 이 일이 든 칸의 정의(처음에는 `haiku-medium`)로 사용자 메시지 분류를 보냅니다. 회고가 칸을 올리면 올라간 칸의 정의로 갑니다 |
| Sonnet high | 계획이 정한 무조건 Opus 영역 단계 구현 「(최저: `sonnet-medium`)」 | 종합 검토를 거친 구현 계획이 SQL, 권한 규칙, 경계 조건, 문구까지 정해 새로 정할 것이 없는 단계입니다 |
| Opus high | 무조건 Opus 영역 판단(결론, 설계, 바깥에 나가는 문구 초안) 「(고정)」 | 「무조건 Opus」 영역의 판단은 작업 크기와 상관없이 이 칸입니다. 사실 조사와 구현은 단계마다 보내는 곳이 다릅니다(`SUBAGENT_GUIDE.md`의 「내려 보기 시험과 「(고정)」」) |
| Opus high | 무조건 Opus 영역 구현 「(고정)」 | 구현 계획이 그 단계를 다 정하지 못해 구현하면서 정할 것이 남은 단계의 작성과 수정입니다. 「구현」은 코드든 문서든 그 영역의 작성과 수정을 말합니다 |
| Opus medium | 자동 회고 「(고정)」 | 회고 방식이 자동일 때 메인이 표에서 이 일이 든 칸의 정의(처음에는 `opus-medium`)로 회고 서브에이전트를 백그라운드로 띄웁니다(`RETRO.md`의 「자동 회고」). 회고가 칸을 올리면 올라간 칸의 정의로 갑니다 |
| Opus medium | 작업 기록 병목 분석 「(고정)」 | 회고가 가장 오래 걸린 일 1건의 작업 기록을 읽어 낭비와 개선안을 찾는 리뷰어입니다. 메인이 표에서 이 일이 든 칸의 정의(처음에는 `opus-medium`)로 보냅니다(`RETRO.md`의 「속도와 비용 보기」). 회고가 칸을 올리면 올라간 칸의 정의로 갑니다 |
| Opus medium | 문서 내용 검토 「(고정)」 | 회고가 스킬과 프로젝트 `CLAUDE.md`의 모순, 중복, 빼도 되는 내용, 보강할 곳을 찾는 리뷰어입니다. 메인이 표에서 이 일이 든 칸의 정의(처음에는 `opus-medium`)로 보냅니다(`RETRO.md`의 「반복 찾기」). 회고가 칸을 올리면 올라간 칸의 정의로 갑니다 |
| Opus xhigh | high로도 안 풀려 다시 보내는 일 | 「문제가 생기면 올리기」에서 Opus high로도 안 풀린 일을 보내는 칸입니다. 마지막으로 Fable 5.1에 보낼 때는 `opus-xhigh`로 부르되 `model`을 `fable`, `effort`를 `high`로 덮어쓰고 사용자에게 먼저 묻습니다(정의 파일과 표 칸은 없습니다) |

## 여러 직군을 고를 때 합치는 규칙

처음 설치에서 직군을 여러 개 함께 고를 때의 규칙입니다.

1. 고른 직군 표를 칸별로 합칩니다. 같은 칸의 일 이름을 모으고, 같은 이름은 하나만 남깁니다. 직군 표들은 같은 일을 같은 이름으로 적어 두었으므로 괄호 앞의 이름이 같으면 같은 일입니다. 괄호 부연만 다르면 부연을 합쳐 하나로 둡니다.
2. 같은 일 이름이 두 칸에 있으면 높은 칸에 둡니다. 모델이 위인 칸(Haiku, Sonnet, Opus 순)이 높고, 같은 모델이면 effort가 높은 칸이 높습니다.
3. 「무조건 Opus」 목록도 합치고, 뜻이 같은 항목은 하나로 둡니다.
4. 합친 뒤 칸의 일 이름이 5개를 넘어도 됩니다.
5. 지시문 체크리스트 기본 줄도 모읍니다. 「지킬 것」 문장이 글자까지 같은 줄은 하나만 남깁니다. 뜻이 같은 줄이 둘 이상 들어가게 되면(직군에 맞게 쓴 코드 리뷰 줄처럼) 한 줄로 합치고, 직군에 따라 다른 부분은 한 문장 안에 함께 적습니다. 같은 일을 맡길 때 어느 줄을 넣을지 두 가지로 읽히는 것을 막으려는 것입니다.

## 지시문 체크리스트 기본 줄

`SUBAGENT_BRIEF_CHECKLIST.md`(지시문 체크리스트, 서브에이전트에 일을 보내기 전에 대조하는 목록)에는 직군과 상관없는 공통 줄만 들어 있습니다. 직군마다 아래 「지시문 체크리스트 기본 줄」 표가 있고, 설치할 때 고른 직군의 줄을 공통 줄에 더해 그 사람의 체크리스트를 시작합니다. 그 뒤로는 회고가 기록을 근거로 줄을 더하고 고칩니다.

- 표는 `| 절 | 지킬 것 | 이유 |` 세 칸입니다. 「절」은 줄이 들어갈 체크리스트의 절 이름이고, 체크리스트에 넣을 때는 「지킬 것」과 「이유」 두 칸만 그 절의 표 끝에 넣습니다. 그 절이 체크리스트에 없으면 문서 끝에 같은 이름의 절과 표 머리줄(`| 지킬 것 | 이유 |`, `|:---|:---|`)을 만듭니다.
- 여러 직군에 맞는 줄은 직군마다 같은 문장으로 들어 있습니다. 여러 직군을 고르면 같은 문장은 한 번만 넣습니다. 직군에 맞게 쓴 줄(프론트엔드와 앱의 화면 결함 조사, 화면 성능 측정, 코드 리뷰 등)이 다른 직군의 줄과 뜻이 같으면 위 「여러 직군을 고를 때 합치는 규칙」 5번대로 한 줄로 합칩니다.
- 줄이 없는 직군(기획과 문서)은 공통 줄만으로 시작합니다.

## 「무조건 Opus」가 무엇인가

작업 크기와 상관없이 Opus high로 보내는 영역입니다. 아래 둘 중 하나에 해당하면 넣습니다.

- 틀리면 되돌리기 어렵습니다. 이미 나간 공지, 지워진 데이터, 출시된 앱 버전처럼 고쳐도 피해가 남습니다.
- 틀려도 겉으로 드러나지 않습니다. 시험이 통과하고 화면이 멀쩡해도 숫자나 권한이 틀려 있을 수 있습니다.

## 백엔드

| | low | medium | high | xhigh |
|:---|:---|:---|:---|:---|
| **Haiku** | 시험 실행과 결과 정리(테스트, 빌드, 린트) | 파일 탐색과 검색, 로그와 설정에서 정해진 값 찾기, 정해진 질문의 공식 문서 확인, 회고 정정 분류 「(고정)」 | | |
| **Sonnet** | 원인이 확정된 작은 수정, 설정값이나 문구 한두 곳 반영 | 구현 계획이 정해진 기능 구현(파일 수와 상관없음), 범위가 정해진 테스트 작성, 형식이 정해진 문서와 보고서 작성, 로그와 쿼리 결과 가공, 코드 정리 검토(/simplify, 찾기만) | 여러 문서 갱신과 누락 점검 「(고정)」, 오래 걸리는 일(긴 구현 계획 실행, 많은 파일의 같은 변경, 긴 재현 실행), 큰 diff의 코드 정리 검토(20파일 넘음), 긴 측정 실행(결과 해석은 메인이 하거나 Opus로), 계획이 정한 무조건 Opus 영역 단계 구현 「(최저: `sonnet-medium`)」 | |
| **Opus** | | 여러 출처를 비교해 결론을 내는 조사(볼 출처 목록을 지시에 줌), 영향 범위 조사(바뀌는 코드를 부르는 곳 전수) 「(고정)」, 문서 검수 2차(독립 재독과 코드 대조) 「(고정)」, 자동 회고 「(고정)」, 작업 기록 병목 분석 「(고정)」, 문서 내용 검토 「(고정)」 | 설계와 구현 계획 종합 검토 「(고정)」, 최종 코드 리뷰 「(고정)」, 원인 찾기(이슈 분석, 원인이 정해지지 않은 결함 수정 포함) 「(고정)」, 무조건 Opus 영역 판단(결론, 설계, 바깥에 나가는 문구 초안) 「(고정)」, 무조건 Opus 영역 구현 「(고정)」 | high로도 안 풀려 다시 보내는 일 |

「무조건 Opus」 기본안:
- DB 스키마 변경과 마이그레이션, 운영 데이터 수정
- 결제, 환불, 잔액처럼 되돌릴 수 없는 금전 기록
- 인증, 권한, 보안
- 동시성, 트랜잭션, 분산 락
- 다른 팀이나 외부가 부르는 API 계약

지시문 체크리스트 기본 줄:

| 절 | 지킬 것 | 이유 |
|:---|:---|:---|
| 동시 작업과 파일 | 생성 단계가 있는 작업(생성 스크립트가 덮어쓰는 원본, 코드 생성물)은 어느 원본을 고쳐야 남는지, 생성물을 누가 언제 다시 만드는지 적는다 | 고친 파일이 다음 생성 때 덮어써지고, 생성물을 다시 만들지 추측하게 된다 |
| 동시 작업과 파일 | 명세(API 문서처럼 동작을 정해 둔 문서)와 구현을 동시에 고치면, 함수 이름이나 필드 이름, 에러 코드처럼 양쪽이 정하는 이름은 어느 쪽이 정하는지 적는다 | 같은 것을 두 이름으로 지어 다시 맞춰야 한다 |
| 동시 작업과 파일 | 결정을 문서에 반영하게 할 때는 그 결정이 걸리는 모듈, API, 서비스를 모두 적고(같은 부품을 쓰는 다른 곳 포함), 다른 서브에이전트가 이미 고친 범위가 있으면 그 범위도 적는다 | 한 곳에만 반영되고 다른 곳은 판정 없이 남는다 |
| 동시 작업과 파일 | 구현 계획의 한 항목만 떼어 넘길 때, 계획에 모든 항목에 걸리는 공통 제약 절이 있으면 그 절도 읽게 한다 | 떼어 낸 지시에 공통 규칙(테스트 실행 방법, 환경 변수)이 빠져 다음 항목이 잘못 시작한다 |
