# 서브에이전트 지시문 체크리스트

목표: 서브에이전트가 지시문만 읽고 같은 모자람과 되돌림 없이 한 번에 맞는 결과를 내게 하는 것이다.
서브에이전트에 일을 보내기 전에 한 줄씩 대조하는 목록이다. 모델 배정, git 금지, 보고 형식은 `SUBAGENT_GUIDE.md`와 `~/.claude/agents/` 정의에 있으니 되풀이하지 않는다.

**고치는 법**: 결과가 모자라고 원인이 지시문이면 아래 표를 고친다. 겹치는 줄은 새 줄을 더하지 않고 고쳐 쓰고, 쓸모없어진 줄은 지운다. 줄이 특정 상황을 전제하면 그 전제를 줄에 적는다. 「이유」는 빠지면 무엇이 잘못되는지 한 구절이다.

## 동시 작업과 파일

| 지킬 것 | 이유 |
|:---|:---|
| 여러 서브에이전트가 같은 시각에 일하면 그 사실을 적고, 같은 파일은 고치기 직전에 다시 읽고 자기 절만 고치게 한다 | 서로의 절을 덮어쓴다 |
| 남이 고치는 폴더는 읽기만 하게 하고 작업 폴더를 따로 정해 준다. 메인이나 다른 실무자가 같은 때 고치거나 새로 만드는 파일과 폴더는 이름으로 적는다 | 같은 원본을 덮어쓰고, 메인이 함께 고치는 줄을 실무자가 어긋남으로 세거나 다시 고친다 |
| 한 일을 몫으로 나눠 맡길 때는 두 몫에 걸치는 항목(같은 값, 몫 밖 원칙의 재서술)을 어느 몫이 낼지 정해 준다 | 두 몫이 같은 지적을 내거나 서로 미뤄 놓친다 |
| 나눠 맡긴 일이 함께 쓰는 시험, 자료, 장치는 고칠 담당 하나와 이름을 정해 알리고, 같은 시험 파일이나 외부 호출을 동시에 쓰면 순서를 정한다 | 같은 것을 두 번 만들거나 서로 고치다 엇갈린다 |
| 확인 명령(grep 같은 검색)이 맡긴 범위 밖 파일에 걸릴 수 있으면 고칠지 보고만 할지 정해 준다 | 범위 밖이라 멈춰 묻는다 |
| 내용을 지우거나 옮긴 뒤의 문서 검수는 저장소 전체를 찾고, 고친 문서는 전체를 코드나 원자료와 대조하게 한다 | 바뀐 절 밖에 옛 문장이 남는다 |
| 고칠 파일(딸린 시험, 문서, 생성물, 사본까지), 새 문장을 넣을 자리, 경계 사례, 써도 되는 명령, 조건, 목표 대조 기준을 처음 지시에 모두 적고, 정하지 않은 것은 짐작하지 말고 보고하게 한다. 도는 중에 범위를 더해야 하면 더하는 것과 함께 이미 끝낸 셈 가운데 다시 할 것을 적어 보낸다 | 범위를 짐작하거나 넣을 자리를 몰라 멈추고, 중간에 더한 범위 때문에 끝낸 셈을 스스로 다시 짜느라 시간이 든다 |
| 결함이 되풀이된 자리를 고치게 할 때는 지적받은 것만 맡기고 「되면」 같은 선택 덧붙임을 넣지 않는다. 넣어야 하면 따로 떼어 검증 방법과 함께 맡긴다 | 덧붙인 기능이 같은 자리에 새 결함을 만들어 리뷰를 한 바퀴 더 돈다 |
| 검토를 거친 코드나 문서를 다시 고치게 할 때는 고치기 전 사본이나 diff를 scratchpad에 남기게 하고 만드는 법(명령, 경로)을 준다 | 고친 부분만 다시 검토할 기준이 없다 |
| git이 추적하지 않는 파일은 `git diff`에 안 나오니 변경 확인을 고치기 전 사본과의 비교로 하게 한다 | 고쳤는지 알 수 없다 |
| 결과물을 복사해 옮기는 일은 원본과 같은지 `diff`로 기계 비교하게 한다 | 눈으로는 달라진 곳을 놓친다 |
| 일하는 중인 서브에이전트에 고칠 것은 한 메시지에 모아 한 번만 보낸다. 같은 파일에 새 일을 얹는 것은 그 에이전트가 측정과 캡처 단계에 들어가기 전에만 하고, 들어간 뒤면 끝난 다음 새로 보낸다 | 잇단 정정을 앞 내용의 취소로 읽고 되돌리며, 측정과 캡처가 끝난 뒤 얹은 일이 이미 한 측정과 캡처를 무효로 만든다 |
| 한 항목에 기준을 둘 이상 줄 때(빠르기와 정확성처럼) 부딪히면 어느 쪽이 먼저인지 적고, 안을 고르게 하면 고르는 기준도 적고, 함께 요구한 조건이 동시에 이뤄질 수 있는지 먼저 확인한다 | 우선순위를 추측하고, 동시에 안 되는 조건을 받아 멈춘다 |
| 지시, 규칙, 문서가 같은 일을 달리 말해 겹칠 수 있으면 어느 쪽을 따를지 적는다 | 따를 쪽을 추측한다 |
| 수치(줄 수, 시간, 크기)를 줄 때는 단위, 세는 대상, 경계 포함 여부를 적는다 | 한도 값이 들어가는지 몰라 추측한다 |
| 「X는 고치지 않는다」 금지를 줄 때는 다른 지시가 X를 건드려야 하지 않는지 보고, 걸리면 허용할 몫을 적는다 | 금지와 부딪힌 일이 남는다 |
| 글자나 값을 가르는 판정 규칙을 줄 때는 바꿀 것과 남길 것의 실제 입력 예시를 둘 이상씩 붙인다 | 판정 경계를 추측해 엉뚱한 문구까지 바꾼다 |
| 같은 판정 일을 여러 실무자에게 묶음으로 나눌 때는 견본 묶음을 먼저 채워 기준을 공통 지시에 적고, 겹칠 때 남길 쪽, 코드 값을 옮긴 표, 손으로 적은 개수, 기준끼리 부딪힐 때의 순서를 미리 정하며, 앞 묶음 보고의 「스스로 정한 기준」을 받는 대로 공통 지시에 보태 뒤 묶음에 넘긴다 | 묶음마다 기준을 추측해 판정이 갈리고 같은 모자람이 묶음 수만큼 쌓인다 |
| 행마다 사실을 확인하는 묶음 일은 서로 기대지 않는 읽기와 찾기를 한 응답에 여러 호출로 보내게 하고, 문서는 한 번에 250줄 안쪽만 읽고 여러 파일을 한 명령으로 이어 출력하지 말게 하며(출력 30KB를 넘으면 잘려 다시 읽는다), 모든 묶음에 같은 기계 확인(경로, 식별자 존재)이 들면 메인이 스크립트로 한 번 돌려 결과를 넘긴다 | 호출을 하나씩 기다리고, 잘린 출력을 다시 읽고, 같은 확인 반복문을 묶음마다 새로 짜 시간이 샌다 |
| 결정 문서나 그 일의 방법 문서에 이미 있는 값, 범위, 목록, 처리(무엇을 걷고 남길지, 화면 목록, 사본 옮기는 때, 지적 등급별 처리, 산출 표의 칸)는 지시에 다시 풀어 쓰지 않고 결정 행이나 방법 문서의 절을 가리키며 「그대로 따른다」고 쓴다. 달리 하려면 방법 문서를 먼저 고친다. 꼭 옮겨 적을 예시와 사실은 보내기 전에 그 행에 대 보고, 걷기로 했지만 코드가 아직 있는 기능처럼 시점이 따로 정해진 것을 함께 적는다 | 대 보라는 줄만으로는 메인이 기억으로 다시 쓴 값이 결정 행과 엇갈린 지시가 하루 일곱 번 나왔다(2026-11-06). 폐기된 정책을 예로 들거나 아직 걷을 때가 아닌 것을 지웠다 되돌린다. 방법 문서보다 넓은 처리와 표 칸을 지시에 다시 정해, 고침 실무자가 판정표 칸을 두 배로 쓰고 권장까지 고쳤다(고침 6회, 판정표 쓰기 334초) |
| 다른 화면, 다른 회차, 다른 목적에서 나온 것(판정 결론, 선례 화면, 옛 산출물, 문구)을 지시에 옮길 때는 `옮겨 온 것:` 줄에 항목마다 규칙 문서 줄(경로:줄)을 붙이거나 「그 화면의 선택(참고)」으로 적고, 「같은 창」, 「같은 틀」처럼 같게 하라는 말에는 같게 할 것과 이 화면에 맞게 바꿀 것(문구, 값)을 나눠 적는다. 규칙 문서에 없는데 규칙으로 쓰려면 규칙 문서를 먼저 고친다. 옮김 말투가 있는데 이 줄이 없으면 `brief-check.js`가 막는다 | 한 화면의 판정이 고른 배치가 다른 화면군 지시와 사용자 보고에 규칙처럼 실렸고, 「같은 창」이라고만 쓴 지시에 다른 화면의 문구가 그대로 옮겨졌다. 판정 파일 경로를 출처로 달아도 규칙이 아니라서 경로만 붙이는 것으로는 막히지 않는다 |
| 생성 단계가 있는 작업은 어느 원본을 고쳐야 남는지, 생성물을 누가 언제 다시 만드는지 적는다 | 고친 파일이 다음 생성 때 덮어써진다 |
| 구조나 배치를 바꾸는 일은 옛 구조가 이름 없이 해 주던 일(정렬, 여백)을 뽑아 적고 새 구조의 담당을 보고하게 한다 | 옛 구조와 함께 그 일이 빠진다 |
| 같은 변경을 여러 개에 적용하게 할 때는 구조가 다른 표본 2~3개로 먼저 시험하게 하고 메인이 표본 결과를 확인한 뒤 전체에 적용하게 한다 | 표본 하나로 전체에 적용해 놓친다 |
| 결정을 문서에 반영하게 할 때는 그 결정이 걸리는 모듈, API, 서비스를 모두 적고 다른 에이전트가 이미 고친 범위도 적는다 | 한 곳에만 반영된다 |
| 참고 문서를 쓰게 할 때는 확인한 사실과 이미 정한 규칙만 쓰고 정하지 않은 금지와 선택 범위를 새로 만들지 말게 한다 | 정하지 않은 규칙이 문서에 박힌다 |
| 산출물에는 지시와 결정에 없는 요소를 넣지 말게 하고, 필요해 보이면 보고에 제안으로 적게 한다 | 넣은 요소를 찾아 지워야 한다 |
| 회차마다 되풀이하는 점검은 통과를 규칙 번호 목록 한 줄과 본 범위로만 받고 근거는 통과가 아닌 것에만 붙이게 하며, 다음 단계가 쓰지 않을 목록(반영하지 않기로 한 다듬기 등)은 요구하지 않고, 답 본문은 보고 첫 줄과 통과가 아닌 번호만 받는다 | 요구 없는 절과 같은 보고 되풀이로 보고 쓰는 시간이 회당 30~40% 더 든다(점검 35회 보고의 25%가 요구 없는 절이었다) |
| 끝났거나 멈춘 서브에이전트는 메인이 확실히 멈춘다 | 늦게 깨어나 파일을 덮는다 |
| 뒤에서 도는 실무자에게는 보고를 끝 메시지에만 두지 말고 정한 파일에도 쓰게 하고 그 경로를 지시에 적는다 | 끝 메시지가 메인에 닿지 않아 보고를 다시 달라 했고, 짧은 답만 와 전체 보고를 또 받았다 |
| 구현 계획의 한 항목만 떼어 넘길 때 계획에 모든 항목에 걸리는 공통 제약 절이 있으면 그 절도 읽게 한다 | 공통 규칙이 빠져 잘못 시작한다 |
| 사용자 지시, 검토 지적, 사용자가 고른 선택지는 내 말로 줄이지 않고 원문이나 원문 경로를 붙인다 | 요약을 다른 뜻으로 읽는다 |
| 지시에 적는 파일 경로, 줄 번호, 함수 자리는 지시를 쓰기 직전에 검색으로 확인해 적고, 맡긴 목록 가운데 지킬 제약(돈이 드는 길 금지 같은)과 부딪히거나 실측이 먼저인 항목은 그 항목 옆에 표시한다 | 실무자가 틀린 줄 번호와 파일을 낱말로 다시 찾고, 부딪힘을 늦게 알아 리뷰에서 되돌린다(모자람 4건, 2026-11-09) |
| 많은 줄을 규칙대로 바꾸는 일은 꼴마다 바꿀 모양을 표로 빠짐없이 주고, 바꾼 줄을 모두 다시 읽게 한다 | 일괄 변경이 문장을 깨뜨린다 |
| 어미나 글자 수로 판정하는 스크립트로 한꺼번에 바꾸지 말게 한다 | 판정이 어긋난 줄까지 바뀐다 |
| `목표:` 줄, 결정 문서 경로(또는 `결정 문서: 없음(까닭)`), 표보다 높은 정의의 `높임:`(올려 다시 보낼 때는 `올림:`)은 훅 `~/.claude/subagent-system/hooks/brief-check.js`가 검사한다(`description`에 표의 일 이름이나 `표에 없는 일: <이름>`이 없으면 막는다). 묶음으로 나눈 판정, 적용, 검수, 점검 일(`묶음 N`이나 `packet-N`이 든 지시)은 `지킬 결정:`(또는 결정어가 든 `~가 정한`, 결정어는 사용자 설정의 호칭이나 `config.json`의 `decisionWords`)과 `부딪힐 때:`가 없으면 막고, 없으면 `없음(까닭)`으로 적는다. 시험 표시가 있는 칸을 시험 정의가 아닌 정의로 보내면서 시험이 2건 아래이면 `시험 건너뜀:`, `높임:`, `올림:` 중 하나를 요구한다. 600자 아래 지시와 haiku 정의는 검사하지 않는다. 훅이 없으면 직접 적는다. 회사 규칙 묶음이 깔려 있지 않으면 훅이 이 검사를 하지 않으니 지시문을 보내기 전에 직접 대 본다 | 판단 기준을 짐작하고, 높임은 회고의 근거다 |
| 회사 규칙 묶음이 깔려 있으면, 작업 문서(`<!-- work-doc -->`)가 있는 일은 `work-bundle.js --work`가 엮은 묶음 파일을 만들어 `묶음: <경로>` 한 줄로 주고, `결정 문서:` 줄에는 그 작업 문서 경로를 쓴다. 지시문에 결정, 규칙, 순서를 다시 풀어 쓰지 않고, 실무자에게는 보고 끝에 묶음 파일의 「규칙 대조」 표를 채우게 한다. 묶음을 엮은 뒤 작업 문서나 공통 결정이 바뀌었으면 `--verify`로 낡았는지 보고 다시 엮는다(회사 규칙 묶음이 깔려 있을 때만) | 결정 문서를 통째로 넘기면 필요 없는 행을 읽다 걸리는 규칙을 놓치고, 지시문에 옮겨 적으면 바뀔 때 갈린다 |
| 결정 문서의 칸은 회사 규칙 묶음이 깔려 있으면 `~/.claude/subagent-system/docs/COMPANY_RULES.md` 「결정 문서」를 따르고, 없으면 사용자 `CLAUDE.md`가 정한 결정 문서 꼴을 따른다 | 칸 기준이 두 곳에 있으면 어긋난다 |
| 명세와 구현을 동시에 고치게 할 때는 번역 키나 클래스 이름처럼 양쪽이 정하는 이름은 구현이 정하고 명세는 나중에 맞춘다고 적는다 | 같은 것을 두 이름으로 지어 다시 맞춰야 한다 |

## 셸과 도구

| 지킬 것 | 이유 |
|:---|:---|
| 여러 에이전트가 로컬 서버나 프로세스를 띄우면 그 사실을 적고, 자기가 띄운 것만 PID로 끄게 한다(이름으로 일괄 종료 금지) | 남의 프로세스가 함께 꺼진다 |
| 임시 파일과 생성 스크립트는 에이전트마다 다른 scratchpad 하위 폴더의 절대경로를 지시에 적고 거기에만 두게 하며 `/tmp`는 쓰지 않게 한다 | 밖에 둔 임시 파일은 지울 때 승인 창이 뜬다 |
| 시험을 돌리게 할 때는 붙여 쓸 시험 명령, 의존성(venv, node_modules) 위치, 린터가 없으면 대신 쓸 확인 방법을 적는다 | 명령을 찾느라 헤매거나 본 폴더에 설치한다 |
| 긴 시험과 1분 넘는 분석 명령(기록 재생, 전수 검색)은 그동안 할 다른 확인이 있을 때만 `run_in_background`로 돌리고, 남은 일이 그 결과뿐이면 앞에서 돌리되(명령 시간 제한 10분) 더 길면 묶음으로 나눠 여러 번 돌리게 한다. 백그라운드로 돌렸으면 기다리는 채로 차례를 끝내지 말고 결과 파일을 직접 확인해 이어 가게 하며, 로그 폴더는 미리 만들게 한다. 출력은 처음부터 로그 파일로 쓰게 하고(`tail`, `head`로 자르지 않음) 실패 이름은 그 파일에서 찾게 하며, 기다릴 때는 완료 알림을 받고 `sleep`이나 `until` 반복문으로 기다리지 않게 한다 | 앞에서 기다리면 회당 몇 분이 빈다(검수 9~12회차에 약 18분). 없는 로그 폴더에 써서 실패한다. 잘린 출력으로는 어느 시험이 떨어졌는지 몰라 5분짜리 전체를 다시 돌렸고, 기다리는 반복문이 셸 제한(180초)에 세 번 걸렸다(2026-11-08 병목 분석). 할 일 없이 백그라운드 결과를 기다리며 차례를 끝낸 실무자 여섯이 완료 알림에 깨지 않아 15~30분씩 멈췄고, 앞에서 나눠 돌리게 한 뒤 넷은 멈춤 0이었다(2026-11-09) |
| 임시 사본 시나리오는 되돌릴 때 승인 창에 걸리는 git 명령(reset, rm, checkout, restore, clean, stash, switch, branch -D)을 쓰지 않고, 시나리오마다 기준 사본을 `cp -R`로 새로 뜨거나 파일을 그냥 지운 뒤 `git add -A`로 되돌리게 한다 | 사본 안에서도 승인 창이 사용자에게 떠 일이 멈춘다(검수 다섯 회차에 17번, 약 27분) |
| 시험 종료 코드는 파이프 없이 `cmd > <로그> 2>&1; echo "EXIT=$?" >> <로그>` 꼴로 남겨 `rg '^EXIT=' <로그>`로 찾게 한다 | zsh에서는 파이프 뒤 코드를 못 잡는다 |
| 확인 칸에는 프로젝트 테스트 문서의 중간 확인 명령과 마지막 전체 명령을 붙이고, 전체는 정리 뒤 한 번만 돌리게 한다. 전체 시험이 실패하면 실패한 시험 파일만 고쳐 돌리고 전체는 마지막 고침 뒤 한 번만 다시 돌리며, 고치는 중에는 전체를 시작하지 않게 한다 | 「전체 통과」만 적은 지시는 전체 시험을 여러 번 돌리게 한다. 정규식 하나를 고칠 때마다 전체(회당 약 3분)를 다시 돌려 한 회차에 일곱 번 돌았고, 도는 판을 `pkill`로 죽이기도 했다(2026-11-09 키트 일 한 회차, 병목 분석) |
| 화면을 고친 뒤 중간 확인은 바뀐 화면 하나와 수치 출력으로 하고, 여러 언어와 폭의 전수 캡처와 시안 대조는 마지막 고침 뒤 한 번만 하며, 중간 그림은 바뀐 한 장만 연다 | 한 줄짜리 CSS나 상수를 고칠 때마다 여러 언어와 폭, 연출 종류별 캡처를 통째로 다시 찍어 여섯 바퀴에 바퀴당 4~10분을 쓰고 그림을 119장 읽었다(2026-11-10 병목 분석). 글자 넘침 같은 끝난 기준은 끝에 한 번만 재면 된다 |
| 사용자 승인이 필요한 외부 동작(메시지 발송, 운영 키 사용, 운영 DB 적용)은 메인이 직접 하고 서브에이전트에는 내용 만들기와 결과 확인만 맡긴다 | 전한 승인을 인정하지 않아 그 단계를 건너뛴다 |
| 서브에이전트에게 보고를 파일로 쓰게 하지 않고 답 본문으로 받으며, 파일이 필요하면 메인이 저장하거나 처음 지시에서 산출물로 정한다 | 저장 요청이 막혀 다시 깨워야 한다 |

## 판단과 리뷰를 맡길 때

| 지킬 것 | 이유 |
|:---|:---|
| opus-high에 판단이나 리뷰를 맡길 때는 미리 받은 조사 결과와 리뷰할 diff 범위를 넣고 그 밖을 넓게 찾지 말게 하며, 더 볼 것은 보고하게 한다 | 싼 모델이 모은 자료를 Opus가 다시 모은다 |
| 사용자가 검수 기준을 직접 정해 준 경우에는 검수 지시문에 그 기준을 빠짐없이 넣고, 더한 기준은 보고의 하고 알린 것에 적는다. 이 체크리스트가 리뷰 종류마다 정한 기준(머지를 막는 기준)은 묻지 않고 넣는다 | 지적이 늘어 검수가 여러 차례 더 돈다 |
| 코드 리뷰에는 「머지를 막는다」의 기준을 적는다: 되돌릴 수 없는 데이터 변경, 다른 기능 회귀, API 계약 깨짐, 테스트가 무작위로 깨짐 | 심각도를 추측한다 |
| 머지 전 메인이 합친 판으로 전체 시험을 돌리는 흐름이면 최종 코드 리뷰 지시문에 전체 시험을 넣지 않고, 구현자 보고의 전체 시험 통과 수와 고친 파일 시험, diff에서 뺀 경로의 시험만 넣는다. 1분 넘는 견주기와 되돌려 보기는 백그라운드로 돌리고 완료 알림을 받게 하며 `sleep`, `until`로 기다리지 않게 한다 | 같은 판의 전체 시험을 구현자, 리뷰어, 메인이 세 번 돌려 리뷰어가 회당 약 1.7분을 기다렸고(19회에 약 34분), 리뷰어 몫 전체 시험에서 나온 결함은 0건이었다. 셸과 도구 칸의 백그라운드 줄이 리뷰 지시문에 옮겨지지 않아 기다리는 반복문이 180초 제한에 걸렸다(2026-11-09 병목 분석) |
| 화면과 앱의 코드 리뷰는 머지를 막는 기준에 접근성 악화, 빌드나 타입 검사 실패, 출시 뒤 고칠 수 없는 설정 변경을 더한다 | 못 고치는 변경이 머지된다 |
| diff에서 뺀 경로가 있으면 그 사실과 그쪽에 기대는 테스트를 돌려 보게 한다 | 깨진 테스트를 늦게 찾는다 |
| 검토자 보고의 지적마다 기계로 잡을 수 있는지(글자나 꼴, 이름 있음, 두 목록 짝짓기, 실행 결과) 표시하게 한다 | 기계로 잡을 지적이 읽는 검수에 되풀이된다 |
| 코드 정리 검토에는 「정한 것을 바꾸지 않는다」가 동작 결과만 가리키는지 코드 모양과 이름까지 가리키는지 적는다 | 정해 둔 모양을 바꾸자는 제안이 나온다 |
| 검토자나 조사자에게 동작을 확인하게 할 때는 확인 수단(읽을 소스 파일, 돌려도 되는 시험 명령, scratchpad 사본)을 정해 주고, `claude` 실행(환경 변수를 붙인 변형 실행 포함)과 Claude Code 세션 띄우기, 패키지 내려받기(`npx -y`, `npm i`, `pip install`)를 금지하며, 그 수단으로 확인할 수 없으면 「확인 못 함」으로 보고하게 한다. 사용자 설정을 읽어 실제로 도는 다른 도구도 같다 | 검토자가 파서를 보려고 `claude` 바이너리를 돌려 사용자 설정으로 실제 세션이 열렸고, 그 세션이 패키지를 내려받았다 |
