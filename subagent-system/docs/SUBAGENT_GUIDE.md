# 서브에이전트 모델 선택 가이드

서브에이전트에 일을 맡기거나, 지시문을 쓰거나, 구현 계획에 모델 표기를 붙이거나, 서브에이전트 결과를 받아 판단할 때 읽는다.

**목표와 지표**: 쓰면 쓸수록 그 사람에게 맞게 스스로 나아지는 서브에이전트 체계입니다. 일마다 알맞은 모델과 effort로 보내 결과의 질을 떨어뜨리지 않고 토큰, 비용, 시간을 줄이며, 질과 비용이 부딪히면 질을 먼저 지킵니다. 지표는 품질(정정과 올림 비율), 비용(일 종류별 토큰과 비용), 성능(걸린 시간)이고, 회고가 이 지표로 표를 고칩니다.

서브에이전트는 **모델과 effort를 함께** 정해 부릅니다. effort는 **`~/.claude/agents/`의 정의**(frontmatter `effort`)로 정하니, Agent 도구의 `effort` 인자는 빼고 정의 이름과 모델을 적습니다. 사용자나 `CLAUDE.md`가 특정 effort로 돌리라고 명시한 때와, 마지막 올리기 단계인 Fable 5.1에 보낼 때(아래 「문제가 생기면 올리기」)만 인자로 넘깁니다. `subagent_type`에 정의 이름(`~/.claude/agents/`의 파일 이름, 예: `sonnet-medium`)을 쓰고, `model`에는 그 정의의 모델(`haiku`, `sonnet`, `opus`)을 적습니다. 정의 없이 부르면 메인 대화의 모델과 effort를 물려받습니다. **스킬과 플러그인이 띄우는 에이전트도 이 규칙으로 정합니다.** 에이전트 정의나 스킬 문서에 모델이 박혀 있어도 부르기 전에 아래 표로 판단하고, 다르면 Agent 호출의 `model`로 덮어씁니다. fork는 모델 지정이 무시되고 메인 모델과 effort로 돌므로, Haiku나 Sonnet으로 충분한 일은 fork 대신 정의로 부릅니다.

- **모델**: 일의 성격으로 고릅니다. Haiku는 찾아 읽고 보고하는 일, 명령을 돌려 결과를 보고하는 일, 요약(파일을 고치는 일은 아래 내려 보기 시험으로만 맡김), Sonnet은 할 일이 정해진 실행에 더해 문서 작성, 분석과 가공, 구현까지 대부분의 일, Opus는 깊은 판단이 필요하거나 틀려도 드러나지 않는 일(원인 찾기, 설계와 종합 검토, 여러 출처를 따져 결론 내기)입니다. 규칙으로 되는 일(짝짓기, 세기, 거르기, 형식 바꾸기, 정해진 대조)은 모델에 맡기지 않고 스크립트로 합니다. **아래 모델일수록 싸고 빠르므로 할 수 있는 일은 최대한 내려 보냅니다.** 메인이 방향이나 안을 정해 줄 수 있으면 정해서 넘깁니다. Sonnet과 Opus 사이가 애매할 때와, 표에 없는 새 일이라 표 위의 모델과 effort 원칙으로도 고르기 어려울 때는 `opus-medium`으로 보냅니다(표에 칸이 있는 일은 표를 따릅니다).
  - Haiku에는 코드와 문서를 고치는 일을 처음부터 보내지 않습니다. 표의 Sonnet low 칸 일에 `haiku-high` 시험 표시가 붙었을 때만 아래 「내려 보기 시험과 「(고정)」」 규칙으로 시험 삼아 보냅니다. 다만 시험을 통과해 회고가 Haiku 칸으로 옮긴 일은 표대로 Haiku로 보냅니다(표의 Haiku 칸에 시험 표시 없이 고치는 일이 들어 있을 수 있고, 표가 회고가 기록으로 고친 값이기 때문입니다).
- **effort**: "얼마나 넓게, 빠짐없이 따져야 하는가". **낮게 보내고, 메인이 결과를 보고 모자라면 올립니다**(토큰 절감). 어느 모델이든 low부터 high까지 쓰고, 칸은 「잘못됐을 때 메인이 알아챌 수 있는가」로 나눕니다.
  - 테스트, 로그, 출처, 메인 확인으로 잘못이 드러나는 일은 낮게 보냅니다.
  - 놓쳐도 아무 신호가 없는 일(최종 코드 리뷰, 종합 검토, 원인 찾기, 「무조건 Opus」 영역의 판단과 검증 등)은 high로 보냅니다. 이런 Opus high 칸과, 이름에 누락 점검, 영향 범위, 검수가 든 일은 표에 「(고정)」을 붙여 내려 보지 않습니다.
  - 오래 걸리는 일(20분 넘게 걸릴 것으로 보이거나 같은 변경을 파일 20개 넘게 반복하는 일)은 low에 두지 않고, Sonnet이면 high로 보냅니다. 낮은 effort에서 긴 일을 빠뜨리거나 일찍 멈추는 것을 막으려는 원칙입니다. 표에 칸이 있는 일은 표가 먼저입니다(표는 회고가 기록으로 고친 값입니다).
  - **xhigh는 처음부터 쓰지 않고, Opus high로도 안 풀린 일을 다시 보낼 때만 씁니다.** max는 쓰지 않습니다.
  - advisor(작은 모델이 큰 모델에게 조언을 구하는 기능)는 켜지 않습니다. 막힘은 메인이 결과를 보고 판단합니다.

- 표가 정의 설명(`~/.claude/agents/`의 description)보다 먼저입니다. 표에 설계와 구현 계획 검토가 있으면, 설계 문서와 구현 계획 작성은 메인이 합니다.
- 표에 코드 정리 검토가 있으면, 거기서 찾은 것을 「무조건 Opus」 영역 코드에 반영하는 일은 Opus high로 보냅니다.
- 표, 아래 「무조건 Opus」 목록, 「사용자 규칙」 구역을 감싼 HTML 주석 세 쌍(「사용자 표」, 「무조건 Opus」, 「사용자 규칙」이라는 이름의 시작과 끝 표시)은 지우지 않습니다. 키트를 업데이트할 때 이 세 사이와 정의 description의 일 이름 나열이 그 컴퓨터의 값으로 지켜지기 때문입니다.
- 표에서 일 이름을 더하거나 빼면 그 칸 정의의 `~/.claude/agents/<정의>.md` description 일 이름 나열도 같게 고치고, `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --check`의 「정의 description과 표 칸이 다른 곳」이 `없음`인지 봅니다.
- 사용자가 빼 달라고 해서 뺀 일 이름은 `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --remove-kind "<일 이름>"`으로 `config.json`의 `removedKinds`에 남깁니다. 회고가 그 이름을 표에 다시 넣지 않고 묻게 하려는 것입니다. 사용자가 다시 넣으라고 하면 표에 넣은 뒤 `--restore-kind "<일 이름>"`으로 뺍니다. 회고 정정 분류, 자동 회고, 작업 기록 병목 분석, 문서 내용 검토, 무조건 Opus 영역 판단, 계획이 정한 무조건 Opus 영역 단계 구현, 무조건 Opus 영역 구현, high로도 안 풀려 다시 보내는 일은 체계가 쓰는 칸이라 빼지 않습니다(빼 달라고 하면 그렇다고 알립니다).

**무조건 Opus(판단과 검증은 high)**: 작업 크기와 무관하게, 틀리면 되돌리기 어렵거나 시험과 검토에서 드러나지 않는 영역입니다.

**규칙을 적을 자리**: 규칙은 언제 판단할 수 있는지로 자리를 정합니다. 한 세션 안에서 보이는 신호로 그 자리에서 판단하고 할 일은 이 문서나 `CLAUDE.md`에 두고, 여러 세션의 기록을 모아야 판단할 수 있는 일(칸 조정, 비율, 누적 반복, 비용 몫)만 `RETRO.md`에 둡니다. 같은 문장을 양쪽에 두지 않고, `RETRO.md`에는 언제 꺼낼지만 두고 방법은 이 문서를 가리킵니다. 키트 문서를 고칠 때와 회고가 아래 사용자 규칙 구역에 줄을 더할 때 이 기준을 따릅니다.

**사용자 규칙**: 이 문서의 공통 문장을 고칠 때(회고든 사용자 요청이든) 아래 구역에 적습니다. 구역 밖은 업데이트 때 키트 문장으로 바뀝니다. 문장을 더할 때는 그대로, 키트 문장을 바꿀 때는 「A 대신 B」로 적습니다. 새로 적는 줄에는 무엇을 막거나 이루려는지 한 구절을 함께 적습니다(목적이 바뀌거나 더 나은 방법이 나왔을 때 고칠 근거가 되게 하려는 것입니다). `RETRO.md`는 업데이트 때 통째로 바뀌므로 그 문장을 바꿀 때는 「RETRO.md: A 대신 B」, 그 절에 줄을 더할 때는 「RETRO.md <절 이름>: B」로 적습니다. 구역 안의 문장이 키트 문장보다 먼저입니다. 회고는 이 구역을 `RETRO.md`보다 먼저 따릅니다. 스크립트가 세는 기준(건수, 비율)은 이 구역으로 바뀌지 않습니다.

**문제가 생기면 올리기**: 서브에이전트가 아래 중 하나에 걸리면 사용자 확인 없이 같은 일을 다시 보냅니다(마지막 Fable 5.1 단계만 예외입니다).
- BLOCKED 또는 NEEDS_CONTEXT 보고
- 같은 일에서 2회 실패
- 지시나 구현 계획에 없는 결정이 필요하다는 보고
- 메인이 결과를 확인했을 때 품질이 모자람 (받은 지시를 지키지 않음, 근거가 빈약함, 글 품질이 낮음)

먼저 지시문 탓인지 가립니다. 서브에이전트 보고 끝의 「지시에서 모자랐던 점」을 근거로 봅니다.
- 맥락, 기준, 확인 방법이 지시에 없었다면 지시문 탓입니다. 지시문 체크리스트에 어느 지시에나 걸리는 문장으로 반영하고, 빠진 내용을 채워 **같은 정의로** 다시 보냅니다. 결과는 `재지시`로 적고 칸은 올리지 않습니다.
- 지시를 다 갖추고도 틀렸을 때만 아래 원인별로 올리고, 결과를 `올림`으로 적습니다.

무엇을 올릴지는 원인으로 고릅니다.
- 파일을 빠뜨렸거나, 확인을 하지 않았거나, 일찍 멈췄으면 **effort를 한 단계** 올립니다.
- 맥락을 다 갖고도 판단이 틀렸거나 결정이 필요하다고 보고했으면 **모델을 한 단계** 올립니다. effort는 표에 그 일의 칸이 있으면 그 칸, 없으면 low입니다. Opus는 위 모델이 없으니 effort를 한 단계 올립니다(high에서 걸리면 xhigh, xhigh에서도 걸리면 아래 Fable 5.1).
- Sonnet은 high 위로 올리지 않고 Opus medium으로 보냅니다.
- Haiku는 파일을 빠뜨렸거나 확인을 하지 않았거나 일찍 멈췄으면 effort를 low, medium, high 순서로 한 단계씩 올립니다. 판단이 틀렸거나, high에서도 같은 원인으로 걸렸으면 모델을 올려 Sonnet low로 보냅니다. 칸을 옮길지는 회고에서 정합니다.
- Opus xhigh로도 안 풀리면 마지막 단계로 Fable 5.1에 보냅니다. 요율표에서 가장 비싼 모델이고, 요금제에 따라 요금제 한도가 아니라 사용 크레딧(추가 요금)으로 청구될 수 있어서 **올리기 전에 사용자에게 묻습니다**(다른 올리기는 묻지 않습니다). 정의 파일은 없어서, Agent 호출에 `subagent_type`은 `opus-xhigh`, `model`은 `fable`, `effort`는 `high`를 직접 넣습니다. 사용 기록은 `--def fable-high`로 적습니다. 호출이 그 모델을 쓸 수 없다고 실패하면 다시 시도하지 않고, `opus-xhigh` 결과와 막힌 점을 사용자에게 보고합니다. 에이전트가 돌지 않았으므로 `fable-high` 사용 기록은 적지 않습니다. 실패하지 않고 끝났어도 다른 모델로 돌았을 수 있으니(조직이 Fable을 막았거나, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`가 켜져 있거나, 보안이나 생물 관련 요청이 안전 분류기에 걸려 그 요청부터 다른 모델로 다시 돌 때, `fallbackModel` 사슬로 다른 모델에서 이어 돌 때, 사용 크레딧 동의 창에서 기본 모델로 바꾸거나 창을 닫았을 때. 이 창이 서브에이전트 호출에도 뜰 수 있다고 보지만 공식 문서로 확인되지 않았습니다) 끝나면 세션을 연 프로젝트 폴더에서 `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --check-fable <agentId>`를 돌립니다(지금 폴더가 세션을 연 폴더와 다르면 `--project <세션을 연 폴더>`를 붙입니다). 이 명령은 기록 폴더의 `subagent-cost.tsv`에서 그 에이전트의 줄을 찾아 모델 열(그 에이전트의 마지막 요청 모델이라 중간에만 바뀐 것은 알 수 없습니다)이 Fable인지 설정과 견주고, 아래 줄을 찍습니다. `CLAUDE_CONFIG_DIR`을 쓰는 컴퓨터는 `$HOME/.claude`를 그 폴더로 바꿔 넣습니다.
  - `판정:`이 `Fable 5.1`이면 Fable 5.1 결과입니다.
  - `Fable 5`이면 Fable 계열로 돈 것입니다. `사용자에게 알릴 말:`을 그대로 알립니다. `rates.json`에는 Fable 5 요율이 없어 비용은 `?`로 남습니다.
  - `Fable(버전 미확인)`이면 `ANTHROPIC_DEFAULT_FABLE_MODEL`로 Fable임은 알았지만 버전은 알 수 없다는 뜻입니다. `사용자에게 알릴 말:`을 그대로 알립니다.
  - `Fable 아님`이면 적어도 끝부분은 Fable이 아니었습니다. 다시 시도하지 않고, `사용자에게 알릴 말:`을 그대로 알립니다.
  - `Fable 확인 못함`이면 모델 열이 공급자 ARN이나 배포 이름이고 설정에서 대응을 찾지 못한 것입니다. 조직 관리 설정의 `modelOverrides`는 읽지 못하므로 `사용자에게 알릴 말:`을 그대로 알립니다.
  - `줄 없음`이면 모델을 확인하지 못한 것입니다. `사용자에게 알릴 말:`을 그대로 알립니다.
  - 사용 기록은 찍힌 `사용 기록 --def:` 값으로 적고, `사용 기록 --memo:` 줄이 있으면 그 줄의 값을 `--memo`에 그대로 씁니다(메모의 첫 단어를 agentId로 읽으므로 agentId가 앞에 오게 찍힙니다). `읽은 설정:`은 판정에 쓴 설정 파일이니 판정이 의심스러우면 거기를 봅니다.

**내려 보기 시험과 「(고정)」**
- 표의 칸 안에 ``「(시험: 다음 1건 `<정의>`)」``가 적혀 있으면, 그 칸의 일을 다음에 1건 그 정의로 보내 보라는 뜻입니다. 결과는 평소처럼 기록하고, 칸을 옮길지는 다음 회고가 정합니다(`~/.claude/subagent-system/docs/RETRO.md`의 「정정과 후보 판정」).
- 보내기 전에 `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --status`의 「시험 표시」 줄에서 그 칸의 상태를 봅니다. `대기`(마지막 회고 뒤 그 정의와 일 종류 기록이 없음)이면 시험 정의로 보내고, `보냄`이면 이미 다른 세션에서 보낸 시험이니 원래 칸의 정의로 보냅니다.
- 이름 뒤의 ``「(최저: `<정의>`)」``는 최저선입니다. 평소에는 그 일을 그 정의 아래로 보내지 않고, 회고의 다시 시험 1건만 예외입니다(`RETRO.md`의 「최저선 다시 시험」).
- 「무조건 Opus」 영역의 일은 영역 전체를 Opus high에 두지 않고 사실 조사, 판단, 구현, 검증으로 나눠 보냅니다.
  - 판단(결론, 설계, 바깥에 나가는 문구 초안)은 「무조건 Opus 영역 판단」으로, 검증은 최종 코드 리뷰로 Opus high에 보냅니다.
  - 사실 조사는 파일 경로, 조문 번호, 출처를 달게 해 메인이 대조할 수 있게 맡기고 표의 일반 칸(파일 탐색과 검색, 정해진 질문의 공식 문서 확인 등)대로 보냅니다.
  - 구현은 종합 검토를 거친 구현 계획이 그 단계의 SQL, 권한 규칙, 경계 조건, 문구까지 정해 구현하면서 새로 정할 것이 없으면 「계획이 정한 무조건 Opus 영역 단계 구현」으로 Sonnet high에 보내고, 정할 것이 남으면 「무조건 Opus 영역 구현」으로 Opus high에 보냅니다. 계획에 없던 결정이 필요하다고 보고한 단계는 Opus medium이 아니라 Opus high로 보냅니다.
  - 최종 코드 리뷰는 영역 단계부터 먼저 보고, 거기서 찾은 결함은 그 단계를 구현한 에이전트의 사용 기록에 같은 agentId로 `올림` 한 줄을 더해 회고가 셀 수 있게 합니다.

**기록과 회고**: 일하는 동안에는 기록만 하고, 표는 **회고**에서 고칩니다(사용자가 표에서 일 이름을 빼 달라고 하면 바로 빼고, 뺀 이름은 위 표 규칙대로 `--remove-kind`로 남깁니다). 회고는 `~/.claude/subagent-system/docs/RETRO.md`를 따릅니다. `미룸` 줄과 `회고` 줄은 손으로 쓰지 않습니다.
- **회고 방식**: `~/.claude/subagent-system/config.json`의 `retroMode`가 정하고, 기본은 `ask`(회고할 때가 되면 사용자에게 묻기)입니다. 파일이 없거나 값이 깨졌으면 `ask`입니다. 바꾸는 것은 사용자가 `/retro auto`와 `/retro ask`로 합니다. 커맨드를 다른 이름으로 설치했으면 `config.json`의 `commandName`이 그 이름이고, 이 문서의 `/retro`는 그 이름으로 읽습니다.
  - 회고가 끝나면(자동 회고는 끝 보고를 받으면) 이 GUIDE를 다시 읽습니다. 정의 파일의 수정은 Claude Code가 몇 초 안에 알아보지만, 표는 메인이 읽는 문서라서 이미 읽은 대화에는 옛 표가 남아 있기 때문입니다.
- 스크립트 명령(`node "$HOME/.claude/subagent-system/scripts/<이름>.js"`)은 어느 폴더에서 실행해도 같은 결과입니다. 경로는 이 문서에 적힌 그대로 씁니다(PowerShell에서 `~`가 풀리지 않음).
- 기록 세 가지(`subagent-usage.tsv`, `subagent-cost.tsv`, `subagent-corrections.tsv`)는 프로젝트와 상관없이 `~/.claude/subagent-system/records/` 한 곳에 모이고(`node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --where`가 이 폴더를 출력합니다), 줄마다 「프로젝트」 열이 있습니다.
- 서브에이전트가 끝날 때마다 메인이 `~/.claude/subagent-system/records/subagent-usage.tsv`에 한 줄 적습니다. 일 종류는 표 칸에 쉼표로 나열된 일 이름 하나를 그대로 적고 부연은 메모에 적습니다(맞는 칸이 없을 때는 아래 새 일 이름 규칙). 결과는 `ok`, `재지시`, `올림` 중 하나이고, 메모 첫머리에는 Agent 결과의 agentId를 적습니다. 결과가 `재지시`이면 메모에 「지시문 탓」과 지시에 빠졌던 것을 한 줄로 적습니다(회고는 같은 칸에 `재지시`가 되풀이되는지 봅니다). 결과가 `ok`여도 서브에이전트 보고 끝 「지시에서 모자랐던 점」이 「없음」이 아니면 메모 끝에 `모자람: <요지 한 줄>`을 붙입니다(회고의 가이드 개선 제안이 이 표시를 근거로 읽습니다). 여러 세션이 같은 파일에 쓰므로 파일을 직접 열어 쓰지 말고 `--log` 명령으로 적습니다.

  ```
  node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --log --project "<세션을 시작한 폴더의 절대 경로>" --def <정의> --kind "<일 종류>" --tokens <토큰> --tools <도구 호출> --secs <걸린 초> --result <결과> --memo "<메모>"
  ```

  - `--project`, `--def`, `--kind`, `--result`, `--memo`는 꼭 줍니다. `--tokens`, `--tools`, `--secs`에는 서브에이전트가 끝난 뒤 돌아오는 완료 알림의 사용량(usage)에서 읽은 값을 주고, 빼면 `-`로 적힙니다. `--date YYYY-MM-DD`를 빼면 오늘 날짜(로컬)로 적힙니다. 필수 값이 빠지거나 결과가 `ok`, `재지시`, `올림`이 아니면 아무것도 쓰지 않고 오류로 끝납니다.
  - `--project`에는 세션을 시작한 폴더의 절대 경로를 줍니다. 워크트리에서 시작했으면 그 경로를 그대로 줘도 `.claude/worktrees/<이름>` 꼬리를 떼어 적습니다. 스크립트가 아는 현재 폴더는 세션 중 `cd`로 바뀌었을 수 있어 생략값으로 쓰지 않습니다.
  - 값은 모두 큰따옴표로 감쌉니다. 값 안의 탭과 줄바꿈은 공백으로 바뀌고, `%`와 작은따옴표는 그대로 적힙니다. 큰따옴표, `$`, 역따옴표(`` ` ``)는 셸이 먼저 풀어 버리니 메모에 넣지 않습니다.
- 회고가 낸 측정 요청을 적용한 일의 결과를 받으면 메인이 `node "$HOME/.claude/subagent-system/scripts/speed-review.js" --measure "<대상>" --items "<항목> <초>, ..."`로 속도 기록에 남깁니다. `<대상>`은 `--pick`이 찍은 `대상:` 뒤 글자 그대로(`칸:<정의>/<일 종류>` 또는 `절차:<프로젝트 경로>/<절차 이름>`)이고, 대상과 항목은 그 측정 요청의 「적용」 칸에 적혀 있습니다.
- 비용은 SubagentStop 훅이 같은 폴더의 `subagent-cost.tsv`에 서브에이전트마다 저절로 덧붙이므로 메인은 적지 않습니다. 요율표, 훅이 빠뜨린 세션을 뽑는 방법은 `~/.claude/subagent-system/docs/RETRO.md`의 「비용 기록」에 있습니다.
- 표에 맞는 칸이 없는 일이면 메인이 짧은 일 이름(표 칸의 이름처럼 명사구)을 새로 지어 일 종류에 적습니다. 괄호는 이름 끝에만 둡니다(가운데 괄호는 스크립트가 이름에서 빼서, 괄호가 든 이름을 기록에 적으면 표 밖 일로 잡힙니다). 짓기 전에 `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --kinds`로 이미 쓴 이름이 있는지 보고, 같은 일이면 그 이름을 그대로 씁니다. `--kinds`에서 `(사용자가 뺐거나 회고가 쪼갠 옛 이름)`이 붙은 이름은 그 일을 맡겼으면 새 이름을 짓지 않고 그대로 적습니다(회고가 표에 넣지 않고 사용자에게 묻습니다). `(회고가 쪼갠 옛 이름)`이 붙은 이름은 적지 않고, 표에 있는 `<이름>[<기준>]` 두 칸 가운데 맞는 쪽을 적습니다. 비슷해 보이는 칸에 억지로 끼워 넣지 않습니다(그러면 회고에서 그 칸의 결과가 섞입니다).
- 이어서 일을 시키면 비용이 그 에이전트 한 줄에 합쳐집니다. 그래서 같은 일을 고쳐 다시 시킬 때(재지시)만 이어서 시키고, 다른 종류의 일은 새 에이전트로 보냅니다. 섞이면 회고에서 일 종류별 비용을 가를 수 없습니다. 재지시하면 그때 결과를 `재지시`로 한 줄 적고, 그 에이전트가 끝나면 같은 agentId로 한 줄 더 적습니다. 스크립트가 결과는 줄마다 세고 비용과 정정은 마지막 줄에만 붙입니다. 재지시 줄의 `--secs`는 그 구간에 걸린 시간만 적으므로, 같은 agentId 줄의 초를 더하면 그 에이전트의 시간입니다.
- 사용자가 서브에이전트 결과의 잘못을 고쳐 말하면, 메인은 같은 agentId로 `--result 올림` 한 줄을 더 적고 메모에 「사용자 정정」과 요지를 적습니다. 회고 시기를 정하는 `--due`는 정정 기록을 읽지 않고 `올림` 줄만 세므로, 이 줄이 없으면 내려간 칸의 질이 떨어져도 다음 회고까지 그대로 남기 때문입니다. 정정의 원인이 지시문이면(메인이 맥락, 기준, 확인 방법을 지시에 빠뜨림) `올림` 대신 `재지시`로 적고 메모에 「지시문 탓」과 지시에 빠졌던 것을 적은 뒤 지시문 체크리스트를 고칩니다. 지시문 탓인 정정까지 `올림`으로 세면 모델은 제 몫을 했는데 칸이 비싼 정의로 올라가기 때문입니다. 원인을 가리기 어려우면 `올림`으로 적습니다.

**오래 걸릴 때**: 짐작으로 모델이나 방식을 바꾸지 않고 시간이 어디서 드는지(모델이 생각하는 시간, 도구 실행과 기다림, 헛걸음) 먼저 재고 큰 곳부터 줄입니다. 잰 결과와 빨라지는 요령은 그 일을 다루는 문서나 지시문 체크리스트에 남깁니다. 잴 때는 `node "$HOME/.claude/subagent-system/scripts/agent-time-breakdown.js" --kind "<일 종류>"`로 모델, 도구, 그 밖의 시간을 나눠 봅니다. 일 종류를 주면 기록이 한 건뿐이어도 봅니다. 지금 도는 에이전트는 사용 기록을 적은 뒤부터 잡히므로, 그 일 종류의 지난 기록으로 어디서 드는지 가늠합니다. 읽는 법은 출력 끝에 있습니다. 여러 번 되풀이되는 긴 일은 회고가 작업 기록을 읽어 낭비를 찾습니다(`~/.claude/subagent-system/docs/RETRO.md`의 「속도와 비용 보기」).

**절차 단계 표시**: 프로젝트가 단계를 정해 둔 절차(검증 절차 등)의 단계를 서브에이전트에 맡길 때는 Agent 도구의 `description` 앞에 `[<절차 이름> <단계 번호>]`를 붙입니다. 예: `[배포 확인 2] 스모크 시험`. 메인이 직접 하는 단계의 Bash 명령에도 `description` 앞에 같은 머리를 붙입니다. 절차 이름은 프로젝트 문서가 그 절차를 부르는 이름을 그대로 씁니다. 글자까지 같아야 같은 절차로 묶입니다. 단계 번호는 프로젝트 문서의 번호를 숫자로 씁니다. 같은 세션에서 표시가 붙은 호출 사이가 60분 넘게 비면 새 회차로 보고, 도중 수정으로 앞 단계를 다시 돈 것은 같은 회차입니다. Bash에 표시를 빠뜨려도 회차는 Agent 표시로 잡히고, 표시 없는 메인 시간은 그 회차의 메인 직접 시간으로 셉니다. 회고가 절차를 한 번 돈 시간을 재어 가장 오래 걸린 일을 찾는 데 쓰는 표시이고, 표시가 없는 옛 기록에서는 절차를 찾지 못합니다.

**지시문**: 보내기 전에 지시문 체크리스트를 대조합니다. 정의 본문에 이미 있는 공통 요구(끝까지 하기, 범위 밖 금지, 근거 붙인 보고, 「지시에서 모자랐던 점」)는 되풀이하지 않고, 일마다 다른 맥락과 기준, 확인 방법을 적습니다. 코드를 쓰는 일에는 주석 기준(정의 본문에 요지가 있습니다)을 지키게 합니다. 표에 코드 리뷰가 있으면, 코드 리뷰는 **머지(바뀐 코드를 본 줄기에 합치는 일)를 막을 문제만** 위치, 왜 틀렸는지, 실패를 보여줄 방법(재현 입력이나 테스트)과 함께 보고하라고 적습니다(막는 기준은 체크리스트의 「판단과 리뷰를 맡길 때」 절에 있습니다. 옛 설치본은 「리뷰」 절입니다). 체크리스트에 두 이름의 절이 모두 없거나 기준이 없으면 되돌릴 수 없는 기록이나 데이터가 바뀜, 다른 기능 회귀, 계약 깨짐 같은 기준을 지시에 직접 적습니다. 메인은 **근거를 확인한 뒤** 결론을 받아들입니다.

**바깥 자료 조사**: 그 분야의 바깥 자료(전문가의 방법, 공식 가이드, 잘 알려진 사례)를 조사해 가이드 문서를 만들자고 제안합니다. 같은 세션의 반복은 메인이 그 자리에서, 여러 세션에 걸친 반복은 회고가 제안합니다(`RETRO.md`의 「반복 찾기」). 제안에는 조사할 질문과 문서를 둘 자리를 적습니다. 사용자가 고르기 전에는 조사하지 않습니다. 고르면 조사는 출처를 달게 해 표의 칸대로 맡기고, 문서에는 적용해 사용자가 승인한 것과 조사만 한 것을 나눠 적습니다.

**git 금지(git 저장소에서 일할 때)**: 직군과 상관없이 git 저장소에서 서브에이전트에 일을 맡기면 이 절을 따릅니다. git 상태를 바꾸는 명령(`commit`, `stash`, `checkout`, `reset`, `merge`, `restore`, `add`, `rebase`, `clean`)은 정의 본문에 이름으로 들어 있고, 지시문에도 **이름으로 열거해** 금지합니다. 「git 상태를 바꾸지 마라」 같은 추상적인 문구만 주면 서브에이전트가 검증하려고 `stash`(작업 중인 변경을 잠시 치워 두는 명령)로 작업 트리를 비우거나 되돌리는 일이 생길 수 있기 때문입니다. 이상을 보면 되돌리지 말고 보고하라고 적습니다. `git worktree`도 서브에이전트는 쓰지 않습니다. '복구했다'는 보고는 메인이 `git status`와 `git stash list`로 직접 확인합니다.
- 검증이 필요한 일에는 stash 대신 임시 사본을 만들거나 영향받는 파일만 시험하는 방법을 지시합니다.
- 그래도 사고가 나면 이 순서로 복구합니다.
  1. 일하는 모든 에이전트에 파일 쓰기를 멈추라고 알립니다. 여럿이 동시에 다시 쓰면 복구가 충돌로 실패합니다.
  2. `git stash list`, `git reflog`, `git status`로 실제 상태를 직접 봅니다. 에이전트의 「복구 완료」 보고는 믿지 않고, stash가 비었는지, 바뀐 파일 수, 일마다 대표 변경이 살아 있는지 확인합니다.
  3. `git stash pop`이나 `drop`처럼 작업 트리를 바꾸는 복구는 사용자에게 상황을 보고하고 허락을 받은 뒤 한 곳에서 한 번에 합니다.
  4. 충돌 표시(`grep -rln "^<<<<<<< "`, Git Bash 또는 터미널에서 실행)가 0건이고 빌드가 통과하면 재개를 알리고, 손대는 파일은 기억에 기대지 말고 다시 읽으라고 함께 지시합니다.
- 원인은 충돌 표시의 이름으로 가립니다. `Updated upstream`과 `Stashed changes`면 stash 충돌이고, `HEAD`나 브랜치 이름이면 merge입니다. `.git/MERGE_HEAD`가 있는지와 충돌 파일의 수정 시각으로 시점을 좁힙니다.

**구현 계획 표기**: 구현 계획 문서를 쓰고 항목별로 서브에이전트에 나누는 방식이면 **항목 제목마다 `[Sonnet high]`처럼 모델과 effort**를 붙이고, 그 표기의 정의로 부릅니다. 그런 문서를 쓰지 않으면 건너뜁니다. 표기 판단도 위 표와 무조건 Opus 영역으로 합니다.
- 계획의 「무조건 Opus」 영역 단계는 구현하면서 새로 정할 것이 남지 않게 SQL, 권한 규칙, 경계 조건, 문구까지 적습니다. 계획 단계에서 정할 수 없고 해 봐야 아는 것(실제 데이터 모양, 기존 함수 동작)은 계획 앞의 사실 조사 단계로 뺍니다.
- 표에 구현 계획 종합 검토가 있으면 그 지시에 영역 단계마다 새로 정할 것이 남았는지 보라고 적고, 남았으면 계획의 결함으로 짚게 합니다.
- 구현 중 계획에 없던 결정이 나와 그 단계를 Opus high로 넘기면, 메인은 그 계획만 고치고 끝내지 않고 빠졌던 것을 이 계획 작성 기준에 같은 종류에 걸리는 문장으로 더합니다(겹치면 그 문장을 고쳐 씁니다).
