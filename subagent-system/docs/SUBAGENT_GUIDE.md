# 서브에이전트 고르기와 맡기기 가이드

목표: 메인이 서브에이전트를 고르고, 맡기고, 결과를 받아 기록할 때 이 문서 하나로 판단해, 결과의 질을 지키며 토큰과 시간을 줄이고 쓸수록 그 사람에게 맞게 나아지게 한다.
서브에이전트에 일을 맡기거나, 지시문을 쓰거나, 서브에이전트 결과를 받아 판단할 때 읽는다. 가끔 쓰는 절(구현 계획 표기, 검토를 끊는 때 등)은 맨 아래 「상황별로 읽는 절」이 가리킨다.
질과 비용이 부딪히면 사용자 CLAUDE.md의 「우선순위」를 따른다. 칸이 없으면 질을 먼저 지키고 사용자에게 한 번 물어 그 칸에 적는다. 까닭: 추측하지 않고 같은 질문을 되풀이하지 않으려는 것이다.
지표는 품질(정정과 올림 비율, 사용자가 더 없냐고 물은 횟수), 비용(일 종류별 토큰과 비용), 성능(걸린 시간)이다.
원칙 한 줄씩은 `~/.claude/rules/kit-core.md`에 있고, 이 문서는 그 원칙을 실행하는 방법만 둔다. 같은 문장은 되풀이하지 않는다. 골라 넣은 권장 규칙(`kit-rec-*.md`)이 없어도 이 문서만으로 맡길 수 있다.

## 부르는 법

서브에이전트는 모델과 effort를 함께 정해 부른다. effort는 `~/.claude/agents/` 정의의 frontmatter `effort`가 정하니 Agent 도구의 `effort` 인자는 빼고, 정의 이름과 모델을 적는다.
- `subagent_type`에 정의 이름(`~/.claude/agents/`의 파일 이름, 예: `sonnet-medium`), `model`에 그 정의의 모델(`haiku`, `sonnet`, `opus`)을 적는다.
- `effort` 인자를 쓰는 때는 사용자나 CLAUDE.md가 특정 effort를 명시한 때와, 마지막 올리기 단계인 Fable 5.1뿐이다.
- Agent의 `description`에는 표 칸의 일 이름을 글자 그대로 넣는다(절차 단계 머리가 있으면 그 뒤에). 사용 기록 훅이 이 글로 일 종류를 적고 지시문 검사 훅이 이 글로 표 칸을 찾아 높임을 검사한다. 이름이 없으면 그 기록은 칸 판정에서 빠지고 높임 검사는 건너뛴다.
- 정의 없이 부르면 메인 대화의 모델과 effort를 물려받는다. fork는 모델 지정이 무시되므로 Haiku나 Sonnet으로 충분한 일은 fork 대신 정의로 부른다.
- 스킬과 플러그인이 띄우는 에이전트도 같다. 정의나 스킬 문서에 모델이 박혀 있어도 부르기 전에 표로 판단하고, 다르면 Agent 호출의 `model`로 덮어쓴다.
- 서로 기다리지 않고, 같은 파일을 고치지 않고, 방향이 정해진 일은 한 메시지에 함께 보낸다. 방향이 불확실하면 한두 개를 먼저 해 본다. 까닭: 틀렸을 때 여럿을 한꺼번에 버리지 않게.
- 맡길 일의 예시(판단은 kit-core의 비용 기준): 파일 셋 이상 읽기, 넓은 검색, 파일 만들기와 고치기, 디버깅과 테스트 실행, 리뷰와 설계 검토, 「조금만 더 보면 알 것 같다」 싶은 때. 파일 둘을 읽고 부족하면 멈추고 맡긴다.

## 모델과 effort 고르기

- 모델은 일의 성격으로 고른다. Haiku는 찾아 읽고 보고하는 일, 명령을 돌려 결과를 보고하는 일, 요약이다. Sonnet은 할 일이 정해진 실행에 더해 문서 작성, 분석과 가공, 구현까지 대부분의 일이다.
  Opus는 깊은 판단이 필요하거나 틀려도 드러나지 않는 일(원인 찾기, 설계와 종합 검토, 여러 출처를 따져 결론 내기)이다.
- 규칙으로 되는 일(짝짓기, 세기, 거르기, 형식 바꾸기, 정해진 대조)은 모델에 맡기지 않고 스크립트로 한다. 까닭: 모델 비용과 틀릴 여지가 없다.
- 아래 모델일수록 싸고 빠르므로 할 수 있는 일은 내려 보낸다. 메인이 방향이나 안을 정해 줄 수 있으면 정해서 넘긴다.
- 표에 없는 새 일이거나 Sonnet과 Opus 사이가 애매하면 `opus-medium`으로 보낸다.
- Haiku에는 코드와 문서를 고치는 일을 처음부터 보내지 않는다. 시험 표시가 붙은 Sonnet low 칸 일만 `SUBAGENT_SITUATIONS.md`의 「내려 보기 시험과 「(고정)」」대로 보내고, 시험을 통과해 회고가 Haiku 칸으로 옮긴 일은 표대로 보낸다.
- effort는 「얼마나 넓게, 빠짐없이 따져야 하는가」다. 낮게 보내고 메인이 결과를 보고 모자라면 올린다. 칸은 「잘못됐을 때 메인이 알아챌 수 있는가」로 나눈다.
  - 테스트, 로그, 출처, 메인 확인으로 잘못이 드러나는 일은 낮게 보낸다.
  - 놓쳐도 아무 신호가 없는 일(최종 코드 리뷰, 종합 검토, 원인 찾기, 「무조건 Opus」 영역의 판단과 검증)은 high로 보낸다. 이런 Opus high 칸과 이름에 누락 점검, 영향 범위, 검수가 든 일에는 표에 「(고정)」이 붙고, 회고가 쓰는 네 일(정정 분류, 자동 회고, 병목 분석, 문서 내용 검토)과 수치 검증에도 붙는다.
  - 20분 넘게 걸릴 일이나 같은 변경을 파일 20개 넘게 반복하는 일은 low에 두지 않고 Sonnet이면 high로 보낸다. 까닭: 낮은 effort는 긴 일을 빠뜨리거나 일찍 멈춘다.
  - xhigh는 표의 xhigh 칸에 든 일(회고가 high로 안 풀린다는 기록으로 올린 일)과 Opus high로도 안 풀린 일을 다시 보낼 때만 쓰고, max는 쓰지 않는다. advisor 기능은 켜지 않고 막힘은 메인이 결과를 보고 판단한다.

## 표와 무조건 Opus

일 종류별 모델과 effort 표, 「무조건 Opus」 목록, 프로젝트별 목록은 `~/.claude/subagent-system/docs/ROUTING_TABLE.md`에 있다. 사용자 데이터라 키트 업데이트가 덮어쓰지 않는다.
- 표가 정의 설명(`~/.claude/agents/`의 description)보다 먼저다. 표에 설계와 구현 계획 검토 칸이 있으면 설계 문서와 구현 계획 작성은 메인이 한다.
- 표에 코드 정리 검토 칸이 있으면, 거기서 찾은 것을 「무조건 Opus」 영역 코드에 반영하는 일은 Opus high로 보낸다.
- 표에서 일 이름을 더하거나 빼면 그 칸 정의의 `~/.claude/agents/<정의>.md` description 일 이름 나열도 같게 고치고, `node "$HOME/.claude/subagent-system/scripts/subagent-retro.js" --check`의 「정의 description과 표 칸이 다른 곳」이 `없음`인지 본다.
- 사용자가 빼 달라고 해서 뺀 일 이름은 `--remove-kind "<일 이름>"`으로 `config.json`의 `removedKinds`에 남긴다. 회고가 그 이름을 다시 넣지 않고 묻게 하려는 것이다. 다시 넣으라고 하면 표에 넣고 `--restore-kind "<일 이름>"`.
  체계가 쓰는 칸(회고 정정 분류, 자동 회고, 작업 기록 병목 분석, 문서 내용 검토, 무조건 Opus 영역 판단, 계획이 정한 무조건 Opus 영역 단계 구현, 무조건 Opus 영역 구현, high로도 안 풀려 다시 보내는 일)은 빼지 않고 그렇다고 알린다.
- 「무조건 Opus」 목록에서 항목을 빼는 것만 사용자 승인을 받는다. 항목을 더하거나 프로젝트별로 나누는 것, 구현을 계획 단계로 나눠 싼 모델에 맡기는 것, Opus 안에서 effort를 낮추는 것은 AI가 짝 시험으로 재서 한다.
- 「무조건 Opus」 영역의 일은 영역 전체를 Opus high에 두지 않고 사실 조사, 판단, 구현, 검증으로 나눠 보낸다.
  - 판단(결론, 설계, 바깥에 나가는 문구 초안)은 「무조건 Opus 영역 판단」으로, 검증은 최종 코드 리뷰로 Opus high에 보낸다.
  - 사실 조사는 파일 경로, 조문 번호, 출처를 달게 해 메인이 대조하고, 표의 일반 칸대로 보낸다.
  - 구현은 종합 검토를 거친 구현 계획이 그 단계의 SQL, 권한 규칙, 경계 조건, 문구까지 정해 새로 정할 것이 없으면 「계획이 정한 무조건 Opus 영역 단계 구현」으로 Sonnet high에, 정할 것이 남으면 「무조건 Opus 영역 구현」으로 Opus high에 보낸다. 계획에 없던 결정이 필요하다고 보고한 단계는 Opus high로 보낸다.
  - 최종 코드 리뷰는 영역 단계부터 보고, 지시문에 단계와 그 단계를 구현한 agentId의 짝을 적는다. 리뷰 보고에는 결함마다 만든 서브에이전트의 agentId를 적게 하고, 찾은 결함은 그 agentId로 `올림` 한 줄을 사용 기록에 더한다.

## 문제가 생기면 올리기

서브에이전트가 아래 중 하나에 걸리면 사용자 확인 없이 같은 일을 다시 보낸다(마지막 Fable 5.1 단계만 예외). 같은 방식의 실패가 되풀이되는 일의 처리는 kit-core를 따른다.
- BLOCKED 또는 NEEDS_CONTEXT 보고
- 같은 일에서 2회 실패
- 지시나 구현 계획에 없는 결정이 필요하다는 보고
- 메인이 결과를 확인했을 때 품질이 모자람(받은 지시를 지키지 않음, 근거가 빈약함, 글 품질이 낮음)

먼저 지시문 탓인지 인재 탓인지 가린다. 서브에이전트 보고 끝의 「지시에서 모자랐던 점」을 근거로 본다.
- 맥락, 기준, 확인 방법이 지시에 없었다면 지시문 탓이다. 지시문 체크리스트에 어느 지시에나 걸리는 문장으로 반영하고, 빠진 내용을 채워 같은 정의로 다시 보낸다. 결과는 `재지시`로 적고 칸은 올리지 않는다.
- 지시를 다 갖추고도 틀렸을 때만 원인별로 올리고, 결과를 `올림`으로 적는다.
  - 파일을 빠뜨렸거나, 확인을 하지 않았거나, 일찍 멈췄으면 effort를 한 단계 올린다.
  - 맥락을 다 갖고도 판단이 틀렸거나 결정이 필요하다고 보고했으면 모델을 한 단계 올린다. effort는 표에 그 일의 칸이 있으면 그 칸, 없으면 low다.
  - Sonnet은 high 위로 올리지 않고 Opus medium으로 보낸다. Opus는 high, xhigh 순으로 올린다.
  - Haiku는 파일 누락, 확인 안 함, 일찍 멈춤이면 effort를 low, medium, high 순서로 한 단계씩 올린다. 판단이 틀렸거나 high에서도 같은 원인으로 걸렸으면 Sonnet low로 보낸다.
  - 비용만 문제인 실패(결과는 맞았으나 비쌈)는 올리지 않고 같은 모델의 effort를 한 단계 낮춘 시험으로 2건 이상 보낸다.
  - 올려 다시 보내는 지시문에는 `올림: <앞 정의와 실패 까닭>` 줄을 넣는다(Fable 단계도 같다). 올린 정의는 일 이름 칸보다 높아서 지시문 검사 훅이 `높임:`을 요구하는데, 이 줄이 있으면 훅이 그 검사를 건너뛴다. 까닭: 처음 보냄의 높임과 올림이 기록에서 섞이지 않게 줄 이름을 나눈다.
- Opus xhigh로도 안 풀리면 마지막으로 Fable 5.1에 보낸다. 가장 비싼 모델이라 올리기 전에 사용자에게 묻는다(다른 올리기는 묻지 않는다). 부르는 법과 끝난 뒤 확인(`--check-fable`)은 `SUBAGENT_SITUATIONS.md`의 「마지막 올리기 단계」에 있다.

## 기록과 회고

일하는 동안에는 기록만 하고 표는 회고에서 고친다(사용자가 일 이름을 빼 달라고 하면 바로 뺀다). 회고 절차는 `~/.claude/subagent-system/docs/RETRO.md`다. `미룸` 줄과 `회고` 줄은 손으로 쓰지 않는다.
- 스크립트 명령 `node "$HOME/.claude/subagent-system/scripts/<이름>.js"`는 어느 폴더에서 실행해도 같다. 경로는 적힌 그대로 쓴다(PowerShell에서 `~`가 풀리지 않는다). `--help`를 주면 사용법만 찍고, 인자의 뜻과 값 꼴은 거기서 읽는다(인자 없이 실행하면 일을 하는 스크립트가 있다).
- 기록은 모두 기록 폴더 한 곳에 모인다(`subagent-retro.js --where`).
  사용 기록 `subagent-usage.tsv`, 비용 기록 `subagent-cost.tsv`, 정정 기록 `subagent-corrections.tsv`, 고침 기록 `fixes.tsv`, 예산 원장 `work-budget.tsv`, 짝 시험 기록 `pair-trials.tsv`다.
- **회고 방식**: `config.json`의 `retroMode`가 정한다. 값은 `auto`(최종 보고 뒤 백그라운드로 회고)와 `ask`(회고할 때가 되면 묻기)이고, 처음 값은 설치 때 고른 사용 방식(`profile`)의 기본값이다(개인용 `auto`, 회사용 `ask`).
  회고 방식은 `/retro auto`와 `/retro ask`로 바꾸고, 개인용을 묻기로 돌리는 법과 실패 뒤 다시 켜는 법은 `RETRO.md` 「권한 확인 창과 연속 실패」에 있다.
  커맨드를 다른 이름으로 설치했으면 `config.json`의 `commandName`이 그 이름이고 이 문서의 `/retro`는 그 이름으로 읽는다.
  최종 보고 뒤 판정 명령(`--due`)의 처리는 `AUTO_RETRO.md`를 따른다. 회고 답의 「고친 파일:」에 이 GUIDE나 `ROUTING_TABLE.md`가 있을 때만 그 파일을 다시 읽는다. 이미 읽은 대화에는 옛 표가 남아 있어서이고, 고치지 않았으면 대화에 있는 것이 최신이다.
- **사용 기록**: 사용 기록 자동 적기 훅이 설치돼 있으면 서브에이전트가 끝날 때 `ok` 줄이 저절로 적힌다. 훅이 없으면 메인이 끝날 때마다 `--log`로 적는다. 비용은 SubagentStop 훅이 `subagent-cost.tsv`에 저절로 덧붙이므로 메인은 적지 않는다(요율표와 빠진 세션 찾기는 RETRO의 「비용 기록」).
  메인은 결과가 `ok`가 아닐 때, 모자람이나 개선거리가 있을 때, 표보다 높여 보냈을 때 같은 agentId로 `--log` 한 줄을 더한다(읽는 쪽이 agentId의 마지막 줄을 쓴다). 인자와 메모 꼴은 `subagent-retro.js --log --help`가 찍는다.
  - `--project`는 세션을 시작한 폴더이고, `--tokens`, `--tools`, `--secs`는 완료 알림의 사용량 값이다. 일 종류는 표 칸의 일 이름 하나를 그대로 쓰고, 표에 맞는 칸이 없으면 `--kinds`로 이미 쓴 이름부터 보고 새 이름을 짓는다.
  - 결과는 `ok`, `재지시`, `올림` 중 하나다. `재지시`이면 메모에 「지시문 탓」과 지시에 빠졌던 것을 적는다.
  - `ok`여도 「지시에서 모자랐던 점」이 「없음」이 아니면 `모자람(<태그>)`을, 일하는 방식과 규칙의 개선거리가 있으면 `개선(<태그>)`을 메모에 붙인다. 코드 개선거리는 보고에만 둔다.
  - 처음 보낼 때 표 칸보다 높은 정의로 보내면 지시문에 `높임: <까닭>`을 적고 메모에도 붙인다. 회고가 표를 고칠지 습관을 고칠지 가르는 근거다. 올려 다시 보내는 것은 `올림:` 줄이고 메모에 `높임:`을 붙이지 않는다.
  - 이어서 일을 시키면 비용이 그 에이전트 한 줄에 합쳐지므로 같은 일을 고쳐 다시 시킬 때(재지시)만 이어서 시키고 다른 일은 새 에이전트로 보낸다. 재지시마다 `재지시` 한 줄을 적고, 끝나면 같은 agentId로 한 줄 더 적는다. 재지시 줄의 `--secs`는 그 구간 시간뿐이라 같은 agentId 줄의 초를 더하면 그 에이전트의 시간이다.
  - 사용자가 서브에이전트 결과의 잘못을 고쳐 말하면 같은 agentId로 `--result 올림` 한 줄을 더하고 메모에 「사용자 정정」과 요지를 적는다. 정정의 원인이 지시문이면 `올림` 대신 `재지시`로 적고 체크리스트를 고친다. 원인을 가리기 어려우면 `올림`이다.
- **예산**: 서브에이전트를 띄우거나 도구 호출이 열 번 넘을 것으로 어림되는 작업(사용자 요청 하나)만 시작할 때와 최종 보고 직전에 `work-metrics.js budget`으로 재고, 사용 기록과 같은 기록 폴더에 쌓는다(인자와 판정 기준은 `work-metrics.js --help`). 질문 답변과 한두 줄 고침처럼 그보다 작은 작업은 재지 않는다. 까닭: 재는 데 도구 호출 셋(list, start, end)이 들어 짧은 요청마다 돌면 문맥 전체를 캐시에서 세 번 더 읽는다. 문턱은 `budget list` 기록으로 고친다.
  - 시작: 일을 정한 뒤 서브에이전트를 띄우기 전에 `budget start`로 토큰과 시간의 어림을 남긴다. 원인 기록은 어림을 잡을 때만 보고 일하기 전에 읽는 규칙 문서로 옮기지 않는다.
  - 중간: 하는 중에 어림을 크게 넘길 것이 보이면 원인과 함께 진행 메시지로 알리고 멈추지 않고 이어 한다.
  - 끝: 최종 보고 직전에 `budget end`. `넘음`이나 `덜 듦`이면 원인을 남기고 보고 ③에 적는다.
- **지표 스크립트(`work-metrics.js`)의 나머지**: `pair add|list`는 `SUBAGENT_SITUATIONS.md`의 짝 시험에서 메인이 쓴다. `unused`와 `asks`는 회고 준비가 돌린다.
- 절차 단계 표시는 아래 「상황별로 읽는 절」의 `SUBAGENT_SITUATIONS.md` 「절차 단계 표시」를 따른다. 회고가 낸 측정 요청의 결과는 `RETRO.md` 「속도 개선과 측정 요청」이 정한 대로 `speed-review.js --measure "<대상>" --items "<항목> <초>, ..."`로 남긴다(`<대상>`은 `--pick`이 찍은 글자 그대로).

## 지시문

- 보내기 전에 지시문 체크리스트(`SUBAGENT_BRIEF_CHECKLIST.md`)를 대조한다. 필수 줄(`목표:`, 결정 문서 경로, 끝난 기준)은 kit-core가 정하고 결정 문서 칸의 기준은 `DOC_WRITING.md` 「결정 문서」에 있다.
- 지시문 검사 훅(`~/.claude/subagent-system/hooks/brief-check.js`)이 `목표:` 줄이나 결정 문서 경로가 없을 때 막는다. 훅이 없는 도구에서는 직접 적는다.
- 정의 본문에 이미 있는 공통 요구(끝까지 하기, 범위 밖 금지, 근거 붙인 보고, 「지시에서 모자랐던 점」)는 되풀이하지 않고 일마다 다른 맥락과 기준, 확인 방법을 적는다.
- 서브에이전트가 「컨벤션 문서에 없음」을 보고하면 메인이 그 컨벤션을 문서에 더한다. 지시에는 이름 규칙을 지키고 임의 접미사를 붙이지 않게 적는다. 까닭: 어긋난 이름이 퍼지지 않게.
- 표에 코드 리뷰 칸이 있으면 머지(바뀐 코드를 본 줄기에 합치는 일)를 막을 문제만 위치, 왜 틀렸는지, 실패를 보여줄 방법(재현 입력이나 테스트)과 함께 보고하라고 적는다. 막는 기준은 체크리스트의 「판단과 리뷰를 맡길 때」 절에 있다.
  그 절이나 기준이 없으면 되돌릴 수 없는 기록이나 데이터가 바뀜, 다른 기능 회귀, 계약 깨짐 같은 기준을 지시에 직접 적는다.
- 메인은 근거를 확인한 뒤 결론을 받는다.

## 보고에 붙이는 표시

최종 보고에 ② 정할 것 칸과 ③ 알아 둘 것 칸이 있을 때의 표시 꼴이다(칸 모양은 사용자 CLAUDE.md나 `kit-rec-report`).
- ③ 알아 둘 것의 항목이 ② 정할 것의 어느 결정에 걸리면 항목 끝에 ` (결정 N에 걸림)`을 붙인다. N은 ②의 번호다. 사용자가 그 결정을 고르면 걸린 항목이 어떻게 달라지는지 한눈에 보이게 하려는 것이다.
- 예산이 `넘음`이거나 `덜 듦`이면 ③에 원인을 한 줄로 쓴다. 서브에이전트를 표 칸보다 높여 보냈거나 올렸으면 그 까닭도 ③에 쓴다.

## git

git 저장소에서 키트 정의가 아닌 에이전트(정의 없이 부르기, fork, 플러그인 에이전트)에 일을 맡기면
지시문에 git 상태를 바꾸는 명령(`commit`, `stash`, `checkout`, `reset`, `merge`, `restore`, `add`, `rebase`, `clean`)을 이름으로 열거해 금지하고, `git worktree`도 쓰지 않게 한다.
키트 정의는 본문에 같은 열거가 있어 되풀이하지 않는다. 사실 하나를 한 곳에만 두려는 것이다.
워크트리에서 일하게 하면 그 절대경로를 주고 본 폴더 경로는 주지 않으며 임시 파일은 scratchpad에 두게 한다.
「git 상태를 바꾸지 마라」 같은 추상적 문구만 주면 검증하려고 `stash`로 작업 트리를 비우는 사고가 난다. 이상을 보면 되돌리지 말고 보고하라고 적고, 검증이 필요한 일에는 임시 사본이나 영향받는 파일만 시험하는 방법을 지시한다.
'복구했다'는 보고는 메인이 `git status`와 `git stash list`로 직접 확인한다. 위험 명령의 까닭, 사고 복구 순서, 프로젝트별 권한 거는 법은 `git-work` 스킬이 있으면 그것을 따른다.

## 상황별로 읽는 절

맡길 때마다는 필요하지 않은 절은 `~/.claude/subagent-system/docs/SUBAGENT_SITUATIONS.md`로 뗐다. 맡기는 세션마다 읽는 양을 줄이려는 것이다. 아래 상황이 오면 그 절만 읽는다.
- 표 칸에 시험, 최저, 고정 표시가 붙은 일을 보낼 때와 짝 시험을 채울 때: 「내려 보기 시험과 「(고정)」」
- Opus xhigh로도 안 풀려 Fable 5.1로 올릴 때와 끝난 뒤: 「마지막 올리기 단계」
- 사용자 지적을 받고 규칙이나 체크리스트를 고쳤을 때, 작업이 끝나 `--due` 마지막 줄에 「그 자리에서 고칠 것」이 있을 때: 「그 자리에서 고치기」
- 서브에이전트 하나가 20분을 넘기거나 같은 일을 여러 번 되풀이할 때: 「오래 걸릴 때」
- 프로젝트가 단계를 정해 둔 절차를 맡길 때: 「절차 단계 표시」
- 구현 계획 문서를 쓰고 항목별로 나눠 맡길 때: 「구현 계획 표기」
- 계획, 디자인, 완료 판단을 분야별로 검토받을 때: 「결정 지점 검토단」
- 검토나 점검의 지적을 받아 고칠 때와 끊을 때: 「검토를 끊는 때」
- 새 모델이나 도구를 들이거나 안 쓰는 도구를 정리할 때: 「새 직원과 도구」
- 맡은 일의 매뉴얼이 없거나 같은 지적이 스크립트나 훅으로도 안 막힐 때: 「바깥 자료 조사」
- 제안을 쌓고, 채택하거나 기각하고, 새 제안을 찾는(탐색) 때: 「제안 목록」
- 피드백을 받아 규칙을 어디에 적을지 정할 때: 「규칙을 적을 자리」
