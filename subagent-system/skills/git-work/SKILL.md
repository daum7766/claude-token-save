목표: 여러 세션과 서브에이전트가 동시에 일해도 서로의 변경이 섞이거나 사라지지 않고, 프로젝트 설정이 허용한 커밋과 머지만 기본 브랜치에 깔끔하게 합쳐지게 한다.

경로와 기본 브랜치 이름은 각 프로젝트 문서가 정한다. 정하지 않았으면 워크트리는 `.claude/worktrees/<이름>`, 브랜치는 `wt/<이름>`으로 만든다.

## 세션 워크트리로 일하는 이유

- 세션이나 에이전트가 동시에 같은 저장소를 고칠 때는 세션 하나에 워크트리 하나, 브랜치 하나를 쓰고 본 폴더는 기본 브랜치를 받아 두는 자리로만 둔다. 세션 여럿이 한 작업 트리를 함께 고치면 서로의 미커밋 변경을 덮거나 한 세션의 커밋에 남의 변경이 딸려 들어가기 때문이다.
- 파일을 고치기 전에 만든다. 파일 수정으로 이어질 시안과 조사, git이 보지 않는 산출물만 만드는 세션도 만든다. 질문 답변과 조회만 하는 세션은 만들지 않고, git 저장소가 아니거나 고칠 파일이 저장소 밖(`~/.claude` 등)이면 만들지 않는다.
- 도구로 세션을 옮길 때 `EnterWorktree`에는 `path`로 넘긴다. `name`만 주면 원격 기본 브랜치에서 갈라져 푸시하지 않은 커밋이 빠진다.
- 서브에이전트는 워크트리를 만들지 않고 세션이 만든 워크트리 안에서만 일한다.
- 도구로 세션을 워크트리로 옮기는 일은 첫 서브에이전트를 띄우기 전에 한다. 도는 중에 옮기면 그 에이전트의 셸 명령이 모두 거절된다. 이미 서브에이전트가 돌고 있으면 새로 띄우지 말고 도는 것이 다 끝난 뒤 옮긴다. Bash의 `cd`는 세션을 옮기지 않는다.
- 워크트리는 작업 트리와 브랜치만 나눈다. 운영 DB, 외부 저장소, 공유 문서는 나누지 않는다.
- 워크트리 세션에서 규칙 문서(CLAUDE.md와 프로젝트가 규칙 문서로 정한 폴더)는 이번에 고치는 중이 아니면 본 폴더 경로로 읽는다. 다른 세션이 머지한 규칙이 워크트리에는 아직 없기 때문이다.
- 본 폴더에만 있는 git 밖 자료는 읽기만 하고 고칠 것은 워크트리로 복사해 고친다. 본 폴더를 고치면 기본 브랜치를 받아 두는 자리가 더러워지기 때문이다.

## 쓰면 문제가 생기는 명령

| 명령 | 무슨 일이 생기나 |
|:---|:---|
| `stash` | stash는 모든 워크트리가 함께 쓴다. 한 에이전트의 `git stash`가 다른 세션의 미커밋 변경까지 통째로 치우고(병렬 에이전트가 많을수록 노출이 크다), 다른 `pop`이 오래 전에 남긴 엉뚱한 stash를 꺼내 충돌을 낸다 |
| `reset`, `restore`, `checkout <파일>`, `clean` | 커밋하지 않은 변경은 되돌릴 기록이 없어 그대로 사라진다 |
| `checkout`, `switch` | 다른 세션이 쓰는 브랜치에서 작업 트리를 바꾼다 |
| `rebase` | 작업 중에 하면 기본 브랜치 변경과 충돌하며 일이 멈춘다. 머지할 때만 한다 |
| `branch -D`, `worktree remove` | 머지되지 않은 다른 세션의 일을 지운다 |
| `push` | 되돌릴 수 없다. 자동 배포가 걸린 저장소는 푸시가 곧 배포다. 사용자 CLAUDE.md의 「올릴 것」과 프로젝트 설정을 따른다 |

## 서브에이전트에게 맡길 때

git 저장소의 일을 맡기면 `~/.claude/subagent-system/docs/SUBAGENT_GUIDE.md`의 「git」를 따른다. 금지할 명령과 워크트리 경로를 주는 법이 거기에 있다.

## 더 읽을 때

- 사고를 복구할 때: `RECOVERY.md`
- 한 파일에 다른 세션의 미커밋 변경이 섞였을 때: `MIXED_COMMIT.md`
- 프로젝트마다 커밋, 머지, push 확인을 걸 때: `PROJECT_PERMISSIONS.md`

## 머지

커밋은 프로젝트 설정이 허용할 때 한다. 설정이 묻게 해 두었으면 확인 창이 사용자의 허락이다.

커밋, 리베이스, 머지, 푸시를 한 번에 지시받으면 빠짐없이 하고 보고에 단계마다 한 일을 적으며, 하지 못한 단계는 그렇다고 적는다.

설정이 묻게 해 둔 저장소에서는 커밋과 머지를 맨 마지막에 한 번에 모아 확인받는다. 답에 따라 파일이 바뀌는 남은 질문을 먼저 모두 끝내야, 승인받은 커밋에 나중에 바뀐 파일이 섞이지 않기 때문이다.

1. 워크트리에서 커밋한다.
2. 워크트리에서 기본 브랜치 위로 리베이스한다. merge 커밋으로 받지 않는다.
3. 본 폴더에서 `merge --ff-only`로 합친다. 실패하면 그사이 기본 브랜치가 움직인 것이니 2부터 다시 한다.

- 리베이스는 머지할 때만 한다. 작업 중에는 하지 않는다.
- 머지 직전 워크트리에 커밋하지 않은 파일이 남아 있으면 stash, `--autostash`, 지우기로 치우지 말고 멈춰 무엇이 왜 남았는지 보고한다.
- 세션이 워크트리에 들어가 있어 본 폴더 명령이 거절되면 `ExitWorktree`(`keep`)로 나와서 합친다. 사용자에게 명령을 넘기지 않는다.
- 본 폴더에 커밋하지 않은 변경이 같은 파일에 있어 git이 거부하면 멈추고 보고한다.

## 리베이스 충돌

- 묻지 않고 양쪽 변경을 보고 직접 푼다. 어느 쪽 의도를 살릴지 사용자의 정책 결정이 필요한 충돌만 묻는다. 「커밋하지 않은 파일이 남았으면 멈춘다」는 규칙은 충돌에 걸리지 않는다. 충돌을 풀며 사용자에게 보이는 결과가 달라졌으면 그것만 알린다.
- 생성 파일은 손으로 합치지 말고 생성 스크립트로 다시 만든다.
- 코드가 겹쳤으면 관련 테스트를 다시 돌린다.

## 정리

- 머지가 끝나면(푸시 지시가 함께 왔으면 푸시까지) 머지 지시가 허락이므로 따로 묻지 않고 그 워크트리를 `worktree remove`로, 브랜치를 `branch -d`로 지운다. 설정이 확인 창을 띄우면 거기서 확인받는다. 이어서 작업하면 새 워크트리를 만든다.
- 머지됐는지는 `git branch --merged <기본 브랜치>`에 드는지로 판정한다.
- 머지되지 않은 다른 워크트리는 다른 세션이 쓰는 중일 수 있으니 지우지 않고 이름만 알린다.
